# 깨진 글자 복구기

인코딩 불일치로 깨진 텍스트를 브라우저에서 복구하는 도구. 서버 없이 클라이언트에서만 동작한다.

입력은 두 가지 — **붙여넣기**와 **파일**. 파일은 txt·csv·srt·json 같은 텍스트 파일의 인코딩을 판별해 UTF-8 로 바꿔 내려주고, ZIP 은 안쪽 한글 파일명을 고쳐 다시 묶어준다. 원본 바이트를 그대로 읽기 때문에 **파일 쪽이 붙여넣기보다 정확하다.**

---

## 빠른 시작

```bash
cd mojibake
npm install          # iconv-lite (테스트용 devDependency)
npm test             # 엔진 추출 + Node·브라우저 벤치마크 (붙여넣기·파일 두 모드)
```

도구 자체를 보려면 `index.html` 을 브라우저로 열면 된다. 빌드 과정 없음, 서버 불필요.

```bash
npm run serve        # 필요하면 로컬 서버로 (http://localhost:3000)
```

**빌드 단계가 없다.** `index.html` · `styles.css` · `content/*.html` 이 그대로 사이트다. 아무 파일이나 브라우저로 열면 그게 실제 화면이고, 배포는 `index.html` · `styles.css` · `content/` · `robots.txt` · `_headers` · `favicon.svg` · `og-image.png` 만 올리면 끝이다 (`test/` · `docs/` · `samples/` · `node_modules/` 는 제외).

고칠 곳:

| 고치고 싶은 것 | 파일 |
|---|---|
| 복구기 동작 · 본문 글 · FAQ | `index.html` |
| 색 · 글꼴 · 여백 | `styles.css` |
| 약관 · 개인정보 · 소개 · 문의 | `content/*.html` |

⚠ **푸터는 5개 파일에 각각 들어 있다.** 하나를 고치면 나머지 넷도 같이 고칠 것. 빌드를 없앤 대가가 이것 하나다.

벤치마크를 따로 돌릴 때:

```bash
npm run bench:node     # 붙여넣기 모드 (Node)
npm run bench:file     # 파일 모드 + BOM·이진·ZIP 가드 (Node)
npm run bench:browser  # 두 모드 다 (Chrome/Edge headless) ← 실사용 기준
```

## 파일 구조

```
mojibake/
├─ index.html         ★ 도구. 이게 곧 사이트의 첫 페이지다
├─ styles.css         ★ 5개 페이지가 공유하는 유일한 스타일 파일
├─ robots.txt
├─ _headers           ★ 보안 응답 헤더. Cloudflare Pages·Netlify 가 읽는다
├─ favicon.svg        ★ 탭 아이콘. 글자 없이 도형만 (한글 글꼴 없는 환경 대비)
├─ og-image.png       ★ 1200×630 링크 미리보기. og:image 태그는 도메인 확정 후
├─ content/           ★ 법적 페이지 4개 (about · privacy · terms · contact)
│                       조각이 아니라 완성된 페이지다. 열면 바로 그 화면이 나온다
├─ samples/           테스트용 깨진 파일. 배포 안 함
├─ package.json
├─ CLAUDE.md          Claude Code용 프로젝트 규칙
├─ docs/
│   └─ 기획서.md
└─ test/
    ├─ cases.js       샘플·깨짐 쌍 정의 + 집계 리포터 (두 러너가 공유)
    ├─ sync.js        index.html 에서 엔진을 추출 → engine.js
    ├─ engine.js      ⚠ 자동 생성. 직접 수정 금지
    ├─ benchmark.js   Node 벤치마크 — 붙여넣기 모드 (빠른 게이트)
    ├─ filebench.js   Node 벤치마크 — 파일 모드 + BOM·이진·ZIP 가드 검사
    └─ browser.js     Chrome/Edge headless 벤치마크 (두 모드 다, 실사용 기준)
```

**중요:** 엔진 코드의 원본은 `index.html` 이다. `test/engine.js` 는 테스트를 돌리기 위해 자동으로 뽑아낸 사본이므로 직접 고치면 다음 `sync` 때 덮어써진다.

## 작업 흐름

엔진(채점 배점, 인코딩 후보, 문자 분류)을 고칠 때:

```
1. index.html 의 <script> 안에서 수정
2. npm test           ← sync + Node 두 벤치마크 + 브라우저 두 벤치마크
3. 네 표를 다 확인
     붙여넣기  Node 하한 80% / 브라우저 하한 82%
     파일      Node·브라우저 하한 74%
4. 브라우저에서 index.html 열어 두 탭 다 실제 동작 확인
```

`npm test` 는 하한 미달이면 exit code 1 로 실패한다. 배점을 건드리면 다른 언어가 조용히 깨지는 일이 잦으므로 반드시 돌릴 것.

브라우저가 없는 환경이면 `npm run bench:node` 만 돌릴 수 있지만, **그 숫자는 실사용 정확도가 아니다** — 아래 [정확도](#정확도) 참고. 브라우저 경로는 `BROWSER` 환경변수로 지정할 수 있다.

## 엔진 구조

`index.html` 의 `<script>` 안, 위에서부터 순서대로:

| 구역 | 역할 |
|---|---|
| `SPEC` | 인코딩별 바이트 구조 정의. `sb`=단일바이트, `mb`=멀티바이트 |
| `MISREAD` | "잘못 읽은 쪽" 후보 목록 |
| `ACTUAL` | "진짜 인코딩" 후보 목록 (20종) |
| `buildEncoder` | 역변환 테이블 생성 + 캐시 |
| `bucket` | 유니코드 코드포인트 → 문자 분류 |
| `score` | 문자 분류 비율로 "그럴듯함" 점수 계산 |
| `narrowMisread` | 입력 성격을 보고 후보를 미리 압축 |
| `attempt` | 조합 전수 시도 |
| `recover` | **붙여넣기 엔트리포인트.** 상위 3개 반환 |
| `confidences` | 확신도 % 계산 |
| `sniffBom` / `looksBinary` / `hasHighByte` | 파일 가드 — 후보 경쟁을 돌릴 필요가 없는 경우를 먼저 걸러낸다 |
| `FILE_PRIOR` | 파일 모드 동점 깨기용 사전 확률 |
| `decodeCandidates` | 바이트를 `ACTUAL` 로 직접 디코딩 + 채점 |
| `validUtf8` | 유효 UTF-8 이면 후보 경쟁 없이 확정 |
| `contentMojibake` | 파일은 멀쩡한데 담긴 글자가 깨진 경우를 `recover()` 로 잡음 |
| `recoverBytes` | **파일 엔트리포인트.** 상위 3개 반환 |
| `parseZip` / `zipInspect` / `zipRebuild` | ZIP 파일명 복구 |
| `recoverLines` | 줄마다 다르게 깨진 입력. 통짜보다 나을 때만 채택 |
| `langHint` | 후보 옆에 붙는 언어 라벨. 단정 가능한 것만 언어 이름, 나머지는 문자 이름 |

### 복구 원리

```
깨진 글자 "ì•ˆ"
  ↓ ① MISREAD 인코딩(CP1252)으로 역변환 → 원본 바이트 복원
EC 95 88
  ↓ ② ACTUAL 인코딩(UTF-8)으로 다시 디코딩
"안"
```

①의 정답을 모르므로 MISREAD × ACTUAL 조합을 전부 시도하고, 결과를 `score` 로 채점해 상위 3개를 고른다.

### 파일은 ①이 없다

`recoverBytes` 는 `attempt()` 를 우회한다. 파일은 원본 바이트를 그대로 갖고 있어 역변환 단계가 필요 없기 때문이다.

```
파일 바이트  BE C6 B3 E7 ...
  ↓ ACTUAL 20종으로 각각 디코딩 → score 로 채점
"안녕..." (euc-kr) / "戚硯..." (euc-jp) / ...
```

①이 없다는 건 손실이 없다는 뜻이기도 하다. `encodeWith` 는 해당 인코딩으로 만들 수 없는 글자를 만나면 후보를 통째로 버리고, 붙여넣기 과정에서는 C1 제어문자가 조용히 사라진다. 파일 경로에는 두 문제가 다 없다.

**채점은 `score()` 를 그대로 공유한다.** 파일 모드 조정은 `FILE_PRIOR` 와 가드 함수로만 한다 — `score()` 를 건드리면 붙여넣기 정확도가 같이 흔들린다.

## 정확도

20개 샘플 × 25가지 깨짐 쌍을 전수 조합하고, 이론상 복구 불가능한 케이스(저장·오독 단계에서 바이트가 소실된 경우)를 제외한 **148건**.

**두 개의 숫자가 있고, 기준은 브라우저 쪽이다.**

| 항목 | Chrome (실사용) | Node (빠른 게이트) |
|---|---|---|
| 1순위 정답률 | **84.5%** | 82.4% |
| 후보 3개 내 포함 | **96.6%** | 86.5% |
| 평균 처리 시간 | 2.3ms | 1.8ms |

> **왜 두 개인가** — 엔진은 `TextDecoder` 의 인코딩 표를 그대로 신뢰하는데, **Node(ICU)와 브라우저(WHATWG index)의 표가 다르다.**
>
> | 인코딩 | Chrome 매핑 | Node 매핑 | 일치 |
> |---|---|---|---|
> | euc-kr | 17,048 | 8,412 | ✗ 두 배 차이 |
> | big5 | 16,773 | 19,594 | ✗ |
> | gbk | 23,814 | 23,814 | ✗ 내용 불일치 |
> | shift_jis | 9,551 | 9,551 | ✓ |
>
> Chrome 은 `C3 9F` 를 `횩` 으로 읽지만 Node 는 U+FFFD 를 낸다. 그래서 Node 벤치마크는 엔진을 과소평가한다 — `utf-8 → euc-kr` 이 Node 에선 0/5, 브라우저에선 5/5 다. 사용자가 쓰는 건 브라우저이므로 `npm run bench:browser` 가 기준이고, Node 쪽은 브라우저 없이 빠르게 돌리는 회귀 게이트로 남겨둔다.

**언어별 1순위** (Chrome 기준)

| 언어 | 1순위 |  | 언어 | 1순위 |
|---|---|---|---|---|
| 한국어 | 100% (21/21) | | 독일어 | 100% (7/7) |
| 프랑스어 | 100% (6/6) | | 폴란드어 | 100% (7/7) |
| 베트남어 | 100% (6/6) | | 태국어 | 86% (6/7) |
| 아랍어 | 83% (5/6) | | 그리스어 | 83% (5/6) |
| 히브리어 | 80% (4/5) | | 중국어 | 78% (14/18) |
| 일본어 | 77% (23/30) | | 러시아어 | 72% (21/29) |

실패 23건 중 **18건은 2·3순위에 정답이 있다.** 후보 3개를 제시하는 UI 설계 덕에 체감 실패는 5건(3.4%)이다.

> **이전 문서의 92.1%는 계측 결함으로 부풀려진 숫자였다.** 벤치마크가 `TextDecoder` 와 `iconv-lite` 의 인코딩 라벨을 섞어 쓰는 바람에, WHATWG 표준에서 `latin1` 이 `windows-1252` 의 별칭이라는 점 때문에 멀티바이트→latin1 오독 케이스가 전부 조용히 탈락했다. 유효 케이스가 76건뿐이었고 그중 72%가 키릴·서구권 단일바이트 오독, `euc-kr` 오독은 **0건**이었다. 자세한 내용은 아래 [최적화 이력](#최적화-이력) 참고.

### 깨짐 쌍별 커버리지

두 러너가 매번 출력한다. 전체 정답률은 어떤 쌍이 몇 건 잡히는지에 좌우되므로, 숫자를 인용하기 전에 이 표를 먼저 볼 것.

| 저장 → 오독 | 유효 | Chrome | Node |
|---|---|---|---|
| utf-8 → latin1 | 20 | 100% | 100% |
| utf-8 → koi8-r | 20 | 100% | 100% |
| utf-8 → windows-1251 | 17 | 100% | 100% |
| utf-8 → gbk | 12 | 100% | 100% |
| utf-8 → windows-1252 | 11 | 100% | 100% |
| euc-kr → latin1 | 7 | 100% | 100% |
| euc-kr → windows-1252 | 7 | 100% | 100% |
| **utf-8 → euc-kr** | 5 | **100%** | **0%** |
| gbk → windows-1252 | 8 | 75% | 75% |
| gbk → latin1 | 8 | 75% | 75% |
| big5 → latin1 | 6 | 50% | 17% |
| shift_jis → latin1 | 5 | 20% | 80% |
| euc-kr → utf-8 | 0 | 이론상 복구 불가 | |

`0건` 쌍은 잘한 게 아니라 **안 잰 것**이다. EUC-KR 바이트를 UTF-8로 읽으면 `�` 로 치환돼 바이트가 소실되므로 원리적으로 복구할 수 없다.

### 파일 모드 정확도

20개 샘플 × 19개 인코딩, 왕복 검사를 통과한 **77건**. 붙여넣기와 달리 깨짐 시뮬레이션이 없다 — 파일은 원본 바이트 그 자체다. 정답 판정도 인코딩 *이름*이 아니라 디코딩 결과 문자열로 한다.

| 항목 | Chrome (실사용) | Node (빠른 게이트) |
|---|---|---|
| 1순위 정답률 | **75.3%** | 76.6% |
| 후보 3개 내 포함 | **88.3%** | 81.8% |
| 평균 처리 시간 | 0.3ms | 0.5ms |

> **붙여넣기 84.5% 와 직접 비교하지 말 것 — 케이스 집합이 다르다.** 파일 벤치는 단일바이트 인코딩 12종을 동등 비중으로 재는데, 그 구간이 아래 설명하는 원리적 동점이라 전체 숫자를 끌어내린다.

**저장 인코딩별** (Node 기준)

| 인코딩 | 정답률 | | 인코딩 | 정답률 |
|---|---|---|---|---|
| utf-8 | 100% (20/20) | | euc-kr | 100% (7/7) |
| gbk | 100% (8/8) | | euc-jp | 80% (8/10) |
| shift_jis | 80% (4/5) | | big5 | 17% (1/6) |
| windows-1250·1251 | 50% | | 그 외 단일바이트 | 0~50% |

**CJK 구간은 사실상 다 맞힌다.** 2.5절의 포지셔닝("CJK 사용자를 위한 mojibake 복구기")과 일치하는 결과다. big5 가 낮은 건 벤치 샘플에 번체 중국어가 없어서 big5 로 저장된 일본어·러시아어만 재고 있기 때문이다 — 그건 원래 못 맞히는 게 정상이다.

**단일바이트끼리는 원리적으로 동점이다**

`score()` 는 문자 *종류*의 비율만 본다. 그래서 같은 바이트를 어떻게 읽든 스크립트는 스크립트라 완전 동점이 난다:

```
Καλημέρα κόσμε  /  КблзмЭсб кьуме  /  ÊáëçìÝñá êüóìå   →  셋 다 105.4점
```

붙여넣기 모드는 `narrowMisread` + `encodeWith` 가 후보를 걸러 이 문제가 드러나지 않는다. 파일 모드는 바이트를 그대로 쓰므로 단일바이트 12종이 한꺼번에 남는다. `FILE_PRIOR` 가 실사용 빈도로 동점만 깨주지만(66.2% → 76.6%), 그리스어·히브리어·아랍어처럼 흔치 않은 쪽은 여전히 2·3순위로 밀린다. 근본 해법은 붙여넣기 모드와 같다 — 언어별 bigram 테이블.

### 알려진 한계

**짧은 입력에서 정확도 급락**
채점은 문자 종류의 *비율*만 본다. `안녕하세요`와 `똠뷁쨉먄`은 둘 다 100% 한글이라 동점이다. 10글자 미만이면 통계가 성립하지 않아 사실상 추측이 된다. 실패 케이스가 짧은 샘플(`Привет` 6자, `你好世界` 4자, `שלום עולם`)에 몰려 있다.

**멀티바이트 → 단일바이트 오독에서 2·3순위로 밀림**
남은 실패 23건 중 18건이 이 유형이다 (`shift_jis→latin1`, `gbk→latin1`, `big5→latin1`). 정답은 후보 안에 있는데 1순위를 못 잡는다. 5차 수정의 길이 축소 신호가 방향은 맞았지만 충분히 강하지 않다는 뜻이다.

**Big5·shift_jis 를 저장 인코딩으로 쓴 비(非)중국어·일본어 샘플**
Big5로 일본어를 저장하는 상황은 현실에서 거의 없다 — 벤치마크가 샘플×쌍 전수 조합이라 생기는 합성 케이스다. 낮은 숫자를 그대로 두되, 실사용 비중은 낮다고 보면 된다.

**UTF-8 → windows-1252 오독은 애초에 절반 이상 복구 불가**
cp1252 는 `0x81 0x8D 0x8F 0x90 0x9D` 다섯 자리가 비어 있어, UTF-8 바이트가 거기 떨어지면 읽는 순간 소실된다. 한글 음절의 15.8% 가 해당하고 5글자 문장이면 58% 확률로 최소 하나가 죽는다. 도구가 받기 전에 끝난 일이라 ftfy 를 포함해 어떤 도구도 못 살린다. 8차에서 이 사실을 UI 안내에 넣었다. **본문 콘텐츠 소재로도 쓸 만하다.**

**붙여넣기 과정의 2차 손상 (도구 밖 문제지만 체감 타율을 가장 크게 깎는다)**
UTF-8→latin1 계열 깨짐에는 C1 제어문자(U+0080~U+009F)가 섞여 있는데, 메신저·웹 입력창·문서 편집기를 거치면 이 문자가 조용히 사라지거나 리터럴 텍스트로 바뀐다. 그러면 바이트가 소실돼 복구가 불가능해진다. 엔진으로는 못 고치므로 UI에서 원인을 안내하는 것으로 대응했다(6차 참고).

**근본 해결책 (미착수)**
언어별 bigram 빈도 테이블. `안녕`은 흔하고 `똠뷁`은 아니라는 걸 구분할 수 있다. 단점은 언어당 수십 KB 번들 증가. 현재 정확도로 충분하다고 판단해 우선순위 낮춤.

**원리적으로 복구 불가 (도구 문제 아님)**
`?` 나 `` 로 바뀐 문자는 바이트 자체가 소실된 것이라 어떤 도구로도 못 살린다. 저장 대상 인코딩이 그 문자를 표현할 수 없었던 경우(예: 한글을 Shift_JIS로 저장)가 여기 해당한다.

### 13차 — 줄마다 다르게 깨진 입력

예시 4줄을 한꺼번에 붙여넣자 전부 키릴 쓰레기가 나왔다. 재보니 **줄 수가 문제가 아니었다.**

```
1~3줄 (같은 유형 euc-kr→latin1)   → 전부 정답
1~4줄 (4번째만 utf-8→cp1252)      → ѕИізЗПјјїд №Э°©ЅАґПґЩ…   전부 깨짐
4줄만                             → 정답
```

같은 유형이면 여러 줄이 **오히려 더 정확하다**(문장이 길수록 채점이 선다). 무너지는 건 **유형이 섞였을 때**다. 복구는 "어떻게 잘못 읽혔는지" 를 하나 가정하고 되감는 것이라, 4번째 줄의 `•…š` 를 `latin1-raw` 가 표현하지 못하는 순간 그 가설이 통째로 탈락하고 후보 전체가 `windows-1252` 로 밀려난다.

**`recoverLines()`** — 줄마다 `recover()` 를 돌려 이어붙이고, **통짜보다 자연스러울 때만** 채택한다. 무조건 줄로 나누면 짧아진 줄에서 정확도가 떨어져 잘 되던 문단이 망가진다.

| | n | 통짜 | 적용 후 |
|---|---|---|---|
| 한 언어·한 유형 문단 | 23 | 21 | **21** (발동 0건) |
| 유형 섞인 입력 | 228 | 3 (1%) | **60 (26%)** |

**정상 문단에서는 규칙이 아예 발동하지 않는다** — 줄별 점수가 통짜를 이기는 일 자체가 없어서 임계값 0~40 어디서도 개악이 0이다. `bench:node` 가 이 두 방향을 같이 재고, **문단 발동 0건**이 회귀 감지선이다. 이득만 재면 잘 되던 입력을 망가뜨리는 변경을 통과시키게 된다.

결과는 랭킹에 섞지 않고 전용 카드로 위에 둔다(부분 복구와 같은 원칙). 대신 이 카드가 뜨면 **랭킹 확신도를 `참고용` 으로 낮춘다** — 통짜 1순위가 쓰레기인데 88% 가 붙던 것이 체감상 핵심이었다.

### 12차 — 결과 언어 라벨

후보 3개를 눈으로 비교할 때 "어느 쪽이 내 언어인지" 를 바로 알 수 있게 각 후보 옆에 라벨을 붙였다.

```

안녕하세요 반갑습니다
```

**문자만으로는 언어를 단정할 수 없다.** 키릴 문자는 러시아어·우크라이나어·불가리아어가 공유하고, 한자만 있는 텍스트는 중국어·일본어·한국어 한자를 구분할 수 없다. 그래서 **확실한 것만 언어 이름을 쓰고**(한글·가나·태국·그리스·히브리·아랍) 나머지는 `키릴 문자`·`한자`·`라틴 문자` 로 물러선다. 이 프로젝트가 확신도·부분 복구에서 지켜온 기준과 같다.

인코딩은 별도의 단서다 — `gbk` 로 저장했다면 중국어권 문서일 가능성이 높다. 스크립트로 판정이 안 될 때만 보조로 쓴다.

| | 결과 |
|---|---|
| 라벨이 실제 언어와 일치 (148건) | **97.3%** (하한 90%로 `bench:node` 가 검사) |

어긋나는 4건은 전부 `会議室A-301 15:00開始` — **가나가 없는 일본어**를 CJK 인코딩으로 저장한 경우다. 한자만으로는 중국어와 원리적으로 구분되지 않고, 일본어를 GBK 로 저장하는 것 자체가 벤치마크의 합성 조합이다. UTF-8 로 저장된 같은 문장은 `한자` 로 정직하게 물러선다.

**부분 복구 섹션에서 가장 크게 달라졌다.** 그 후보들은 채점상 전부 동점이라(알려진 한계 참고) 순서가 판단 결과가 아니었는데, 이제 선택 근거가 생겼다:

```
[부분] 한국어   안녕하세�
[부분] 일본어   照括馬室�
```

### 11차 — 본문 예시 정정 + CJK 예시 추가

10차에서 예시 표를 넣으면서 **틀린 설명을 같이 실었다가 고쳤다.** 처음엔 "일본어·중국어 깨짐은 제어문자가 섞여 복사하는 순간 망가지므로 예시로 못 싣는다" 고 적었는데 **둘 다 사실이 아니었다.**

- **브라우저는 C1 을 온전히 보존한다.** headless Chrome 실측 — HTML 소스에 그대로 박은 `U+0080 U+0085 U+009F` 가 파싱·textarea 왕복·선택 영역(복사되는 값)에서 전부 유지됐다. 내 샘플을 망가뜨린 건 **bash 셸** 이었지 사용자 경로가 아니었다.
- **C1 은 언어가 아니라 오독 인코딩의 속성이다.** `latin1` 오독 26/48(54%), `windows-1252`·`koi8-r`·`windows-1251`·`gbk`·`euc-kr`·`shift_jis` 는 **전부 0%**. 언어별로는 일본어 30% / 한국어 19% / 중국어 17% 로 전체 148건 중 26건(18%)일 뿐이다.

실제로 C1 이 0개인 일본어(`shift_jis→windows-1252`)·중국어(`gbk→windows-1252`) 샘플이 얼마든지 있었다. 오독 인코딩 7종만 훑고 성급히 결론지은 것이 원인이라, **이후로는 `test/examples.js` 가 대신 판정한다** — index.html 의 표를 직접 파싱해 붙여넣기·파일 두 경로 정답, C1·NBSP 0개, 숫자 문자 참조 없음을 매번 확인한다.

> **이 표는 나중에 걷어냈다.** 실제 사용자는 자기 깨진 글자를 갖고 오므로 예시가 필요 없는데, 그게 도구 바로 아래 자리(701자)를 차지해 정작 실패한 사용자가 봐야 할 "안 될 때"(당시 347자)를 아래로 밀어냈다. 아래 최신 항목 참고. 이 절은 그때의 판단 근거를 남기기 위해 그대로 둔다.

### 10차 — "내용이 깨진 파일" 처리

9차 파일 탭을 실사용하자마자 나온 구멍. **깨진 글자를 복사해 메모장에 저장한 파일**은 깨진 파일이 아니다 — 바이트는 정상 UTF-8 이고 담긴 글자만 mojibake 다. 그런데 이게 실사용에서 가장 흔한 경로다.

결함이 두 개 겹쳐 있었다:

| | 증상 |
|---|---|
| 인코딩부터 틀림 | `¾È³çÇÏ¼¼¿ä` 가 담긴 UTF-8 파일 → **gbk 판정** → `戮脠鲁莽脟脧...` |
| 맞게 골라도 멈춤 | `GrÃ¼ÃŸe...` → utf-8 확정 → 내용 그대로 반환 |

첫 번째 원인이 흥미롭다. 깨진 글자는 라틴 보조 문자뿐이라 `score()` 가 낮게 주는데, **같은 바이트를 GBK 로 읽으면 한자가 나와 스크립트 110점을 받는다.** `strictUtf` 가점 +70 으로는 이걸 못 이긴다.

**수정 — 둘 다 같은 체인으로 풀린다**

- **유효 UTF-8 은 경쟁시키지 않고 확정.** 파일 벤치의 비 UTF-8 케이스 57건 중 유효 UTF-8 인 것은 **0건**이라 기존 정확도를 하나도 안 건드린다.
- **확정된 텍스트를 붙여넣기 모드로 한 번 더.** `recover()` 재사용, 새 로직 없음.

`CONTENT_GAIN=25` 로 게이트한다 — 정상 텍스트 20건의 개선폭 최대가 20, 깨진 텍스트 148건 중 137건이 25 초과. **오탐 0/20.** 10으로 낮추면 정상 한국어·일본어가 15~20을 받아 오탐 8/20 이 된다.

놓치는 11건은 키릴·그리스어 **동점 계열**이다. `Ñåãîäíÿøíåå`(라틴 악센트 110점) ↔ `Сегодняшнее`(키릴 110점) 은 개선폭이 **정확히 0** 이라 어떤 임계값으로도 못 잡는다. 9차의 단일바이트 동점과 같은 뿌리다.

**섞인 파일은 원리적으로 복구 불가** — 복구는 "어떻게 잘못 읽혔는지" 하나를 가정하고 되감는 것이라, 서로 다른 깨짐이 섞이면 `encodeWith` 가 전부 null 을 낸다. `MOJI_HINT=0.5` 로 사유만 안내한다(결과는 안 바꾼다).

**같이 넣은 것 — 본문 예시 표.** "뭘 넣어야 할지 모르겠다" 는 기획서 5.2 가 미해결로 남겨둔 문제다. 정적 표로 풀었다 — 버튼이 아니고 입력창 우측 상단도 아니다(예전에 그 자리 버튼이 언어 전환기로 오인돼 걷어낸 이력). 이때 실은 설명이 틀려서 11차에서 고쳤다.

### 9차 — 파일 입력 (붙여넣기 / 파일 탭)

붙여넣기 경로에는 구조적 손실이 있다. `encodeWith` 는 해당 인코딩으로 만들 수 없는 글자를 만나면 후보를 통째로 버리고, 8차에서 확인했듯 붙여넣기 과정에서 C1 제어문자가 조용히 사라진다. **파일은 원본 바이트를 그대로 갖고 있어 이 단계 자체가 없다.**

`recoverBytes` 를 추가해 `attempt()` 를 우회하고, 입력 UI 를 탭 두 개로 나눴다. `score()` 는 손대지 않았다 — 붙여넣기 82.4% / 84.5% 는 그대로다.

**실측으로 기각한 것 두 가지**

| 시도 | 결과 |
|---|---|
| 5차의 길이 축소 가점을 파일 모드에 이식 | 브라우저 **68.8%** (제거하면 75.3%). 독일어 29% ↔ 100% |
| 인코딩 후보 확장 (`windows-874`·`iso-8859-8`·`windows-1258`·`iso-8859-5`) | 1순위·3개내 **둘 다 무변화** |

길이 축소 가점은 "입력이 이미 깨진 것이 확실할 때 정답은 짧다"는 전제에 기댄다. **파일에는 그 전제가 없다.** 오히려 단일바이트 파일을 아무 CJK 인코딩으로 읽으면 글자 수가 반으로 줄어 가점을 챙긴다. Chrome 은 euc-kr 을 Node 의 두 배로 매핑하므로 이 엉터리 후보가 훨씬 잘 살아남는다 — Node 에서는 무변화인데 브라우저에서만 6.5%p 차이가 난 이유다.

후보 확장이 무의미하다는 건 6차 결론(20종 → 37종이 84.2% → 81.6%)의 재확인이다. **채점이 약한 신호라 후보를 늘리면 오답에 기회만 준다.**

**대신 넣은 것 — `FILE_PRIOR`**

단일바이트 인코딩 12종은 `score()` 상 완전 동점이라 배열 순서로 갈린다. 그러면 windows-1251 이 항상 이겨 서유럽 파일이 전부 키릴로 나온다. 실사용 빈도를 최대 6점짜리 가점으로 줬다 — `score()` 의 신호 차이는 보통 45점 단위라 근거가 있을 때는 뒤집지 못한다. **66.2% → 76.6%, 독일어·프랑스어 29·40% → 100%.**

**같이 처리한 것**

- **가드** — BOM(`EF BB BF` 등) / NUL·제어문자 5% 초과(이진) / 0x80 없음(ASCII) 은 후보 경쟁을 아예 돌리지 않고 사유를 표시한다. 이진 가드가 없으면 PNG 헤더 16바이트가 `‰PNG ÿØ«` 같은 결과로 확신도까지 달고 나왔다.
- **엑셀 BOM 옵션** — 엑셀은 BOM 없는 UTF-8 CSV 를 로컬 코드페이지로 읽어 **다시 깨뜨린다.** "엑셀 csv 한글 깨짐" 의 실제 해결책은 인코딩 판별이 아니라 이쪽이라, 내려받을 때 BOM 을 붙이는 옵션을 뒀다(`.csv`/`.tsv`/`.txt` 기본 켜짐).
- **ZIP 파일명 복구** — GP flag bit 11 이 없으면 파일명이 로컬 코드페이지로 저장된다. 이름을 전부 이어붙여 한 덩어리로 판별하고(이름 하나는 짧아 통계가 안 선다), 압축 데이터는 그대로 복사한 채 헤더만 다시 쓴다. **inflate/deflate 가 필요 없어 외부 의존성이 0 이다.** ZIP64·암호화·분할 아카이브는 거부한다.
- 20MB 상한. 판별은 앞 64KB 샘플로 하고 확정된 인코딩으로 전체를 디코딩한다.

### 7차 — 부분 복구 표시

바이트가 하나 빠진 입력에서 1순위로 무관한 키릴 문자가 나오던 문제. `안녕하세요` 의 EUC-KR 10바이트 중 `BC` 하나가 빠진 9바이트를 넣으면 `ѕИізЗПјїд` 가 1등이었다.

**점수로는 못 푼다.** FFFD 가드를 풀고 재보면 키릴 쓰레기 110.0 vs 부분 복구 36.0 — 74점 차이다. 비율 기반 채점에서 "전부 한 가지 스크립트"인 쓰레기는 항상 만점을 받는다. 이걸 뒤집을 만큼 배점을 흔들면 러시아어 정답 29건이 무너진다.

**그래서 점수 경쟁에 넣지 않았다.** 랭킹 산출 경로는 그대로 두고, `attempt()` 가 버리던 FFFD 후보 중 조건을 만족하는 것만 따로 모아 랭킹 **아래** 별도 섹션에 나열한다.

채택 조건 — `` 가 **정확히 1개**이고 **맨 끝**에 있으며(= 바이트가 하나 빠져 짝이 안 맞는 형태), 그것을 뺀 나머지의 `score()` ≥ 105, 나머지 길이 ≥ 3.

**어느 것이 맞는지는 판정하지 않는다.** FFFD 를 뺀 나머지로 채점하면 `안녕하셀` `照括馬漆` `救崇窍伎` 가 전부 110.0 동점이다. 언어 사전 없이는 구분할 수 없어(M5 bigram) 읽히는 대로 나열만 하고, 순위·확신도는 붙이지 않는다.

정확도 무변동(Node 82.4% / Chrome 84.5%). 벤치마크 148건 중 섹션이 뜨는 건 4건(2.7%)이고 그중 3건은 1순위가 이미 정답이라 무해하다.

### 6차 — 브라우저 실측 도입 + 가짜 답 제거

**(1) Node 벤치마크가 엔진을 과소평가하고 있었다.** 엔진은 `TextDecoder` 표를 그대로 쓰는데 Node(ICU)와 브라우저(WHATWG index)의 표가 다르다. euc-kr 은 Node 8,412쌍 / Chrome 17,048쌍으로 두 배 차이다. `test/browser.js` 를 추가해 Chrome headless 에서 실제 엔진을 돌린 결과 **84.5% / 후보 3개 내 96.6%** — Node 기준(82.4% / 86.5%)보다 높고, `utf-8 → euc-kr` 은 Node 0/5 → 브라우저 5/5 다.

케이스 정의는 `test/cases.js` 로 분리해 두 러너가 공유한다.

**(2) `encodeWith` 의 `0x3F` 주입 제거.** 역변환 테이블에 없는 문자를 만나면 최대 2%까지 `?` 를 밀어넣고 진행하던 코드를, 후보 자체를 버리도록 바꿨다. 바이트가 오염된 결과가 높은 점수를 받아 이런 걸 1순위로 내놓고 있었다:

```
입력 "ȳϼ"   → 1순위 "??"
입력 "류 생"  → 1순위 "? ?"
```

정확도 손실 0 (Node 82.4%, Chrome 84.5% 그대로), 가짜 답만 사라졌다. `?` 는 복구 불가 신호라고 UI 에서 안내하면서 엔진이 `?` 를 만들어내던 모순도 해소.

**(3) 진단 UI.** 실패했을 때 "되돌릴 조합을 찾지 못했습니다" 한 줄만 띄우던 것을, 원인별로 구분해 안내한다 — `` 소실 / `?` 치환 / **붙여넣기 과정의 C1 제어문자 소실** / 짧은 입력. 마지막 항목은 실사용 타율을 가장 크게 깎는 요인인데 엔진으로는 못 고치므로 안내로 대응한다. 아울러 10자 미만 입력에서는 확신도 %를 숨기고(근거 없는 숫자), 이미 정상인 입력에서는 후보를 "참고용"으로 표시해 강조를 뺐다.


### 5차 — 길이 축소 신호 (81.1% → 82.4%)

계측을 고치자 드러난 편향: `score()` 는 문자 종류의 **비율**만 보는데, 2바이트→1바이트 오독은 글자 수가 2배로 불어나 스크립트 비율이 100%에 수렴한다. 반면 정답은 공백·숫자·문장부호(45점)가 섞여 비율이 희석된다. **공백이 섞인 현실적인 CJK 문장일수록 오답이 구조적으로 유리했다.**

```
입력: 오늘 회의는 오후 3시에 시작합니다.   (EUC-KR → latin1 오독)
  이전  1순위 98.5  "їАґГ ИёАЗґВ їАИД 3ЅГ…"   ← windows-1251 오독
        2순위 90.5  "오늘 회의는 오후 3시에 시작합니다."
```

mojibake 복구의 정답은 거의 항상 입력보다 **글자 수가 줄어든다**(2~3바이트가 1글자로 합쳐지므로). 단일바이트→단일바이트 오독은 길이가 그대로다. 이 신호를 `attempt()` 에 가점으로 넣었다 — `strictUtf` 보너스와 같은 자리, 같은 방식:

```js
sc += Math.max(0, 1 - t.length / s.length) * 30;
```

러시아어 72% → 79%, 한국어 100% 유지, 떨어진 언어 없음. 계수 30은 20~60 구간이 전부 동일한 결과를 내는 평탄 구간의 중앙값이고, 80부터 퇴행한다.

**같이 시도했다가 기각한 것**

| 가설 | 결과 |
|---|---|
| `ascii`/`ws`/`punct` 배점 45 → 75 | 전체 81.1% 그대로, **한국어만 100% → 90%** 로 퇴행. 기각 |
| 정규화 분모에서 공백 제외 | 전체·언어별 전부 무변화. 복잡도만 늘어 기각 |

### 4차 — 계측 결함 수정 (엔진보다 벤치마크가 문제였다)

`benchmark.js` 가 깨짐 생성은 `TextDecoder`, 왕복 검증은 `iconv.encode` 로 서로 다른 라벨 체계를 쓰고 있었다. WHATWG 표준에서 **`latin1` 은 `windows-1252` 의 별칭**이라 진짜 ISO-8859-1 이 아니다. 두 체계가 어긋나는 조합은 왕복 검사에서 탈락해 조용히 사라졌고, 그 결과:

- 유효 케이스가 76건뿐이었고 그중 72%가 키릴·서구권 단일바이트 오독
- `euc-kr` 오독 **0건** — 한국에서 "뷁체"라 부르는, 이 도구의 존재 이유인 케이스
- 엔진이 "실제 깨짐에서 매우 흔하다"고 주석까지 단 `latin1-raw` 경로가 한 번도 안 밟힘

라벨을 `iconv-lite` 로 통일하고 멀티바이트→latin1 쌍 7개를 추가하니 유효 케이스가 **76 → 148건**, 정답률은 **92.1% → 81.1%** 가 됐다. 숫자가 떨어진 게 아니라 원래 그 값이었다.

### 1~3차 — 채점 배점 (70.2% → 92.1%, 구 측정 기준)

> 아래 숫자는 계측 결함이 있던 76건 매트릭스 기준이다. 수정 방향 자체는 유효하지만 값은 그대로 비교하지 말 것.

**1. UTF-8 엄격 검증 보너스 (+70점)**
UTF-8은 멀티바이트 구조가 엄격해 무작위 바이트가 유효할 확률이 낮다. 반면 단일바이트 인코딩은 어떤 바이트든 항상 디코딩에 성공해 변별력이 없다. `fatal: true` 로 한 번 검증해 통과하면 가산점.

**2. 악센트 배점 55 → 110**
스크립트(한글·한자·키릴)는 110점인데 악센트 문자는 55점이었다. 라틴 언어의 정답은 대부분 ASCII+악센트 소수라서, 키릴로 오독된 오답에게 구조적으로 밀렸다. 독일어·프랑스어 정답률 0%의 원인.

**3. 문자 분류 범위 확장**
`ACCENT` 가 서유럽+터키어 문자만 손으로 나열한 집합이었다. 폴란드어 `ł ż ć ę`, 체코어 `č ř ů`, 헝가리어 `ő ű` 가 전부 `latinodd`(-150점)로 분류돼 정답이 벌점을 받았다. Latin Extended-A(U+0100~U+017F) 전체를 `accent` 로 편입하고, 베트남어 성조 문자가 있는 Latin Extended Additional(U+1E00~U+1EFF)도 추가.

### 시도했다가 되돌린 것

**인코딩 후보 확장 (18종 → 36종)**
브라우저 `TextDecoder` 가 지원하는 37종을 전부 후보에 넣어봤더니 정확도가 **84.2% → 81.6% 로 하락**하고 속도는 50% 느려졌다. 채점이 약한 신호라서 후보가 늘면 정답이 이길 확률이 아니라 오답이 정답을 이길 기회가 늘어난다. 되돌림.

다만 실사용 빈도가 높은 `iso-2022-jp`(일본어 이메일)와 `gb18030`(중국 국가표준) 두 개는 손해 없이 커버 범위만 넓혀서 유지 중(총 20종).

## 기존 라이브러리 비교 (ftfy)

[ftfy](https://github.com/rspeer/python-ftfy)는 mojibake 복구의 사실상 표준 라이브러리다.

**측정 방법** — 위 148건 매트릭스(20개 샘플 × 25개 깨짐 쌍, 12개 언어)의 깨진 문자열을 그대로 `ftfy.fix_text()` 에 넣어 원문과 일치하는지 비교. 구간은 *잘못 읽은 인코딩* 기준으로 나눴다.

| 구간 | n | ftfy 6.3.1 | 이 도구 (Chrome) |
|---|---|---|---|
| 전체 | 148 | 24.3% | **84.5%** |
| UTF-8 → 서구권 오독 (ftfy 주력) | 31 | **96.8%** | 100% |
| CJK 인코딩으로 오독 | 20 | **0.0%** | **100%** |
| 키릴 인코딩으로 오독 | 39 | 15.4% | **97.4%** |
| CJK 원문이 깨진 경우 | 51 | **0.0%** | **66.7%** |

**ftfy가 나쁜 게 아니라 대상이 다르다.** 자기 영역(`â€™` 계열 — UTF-8을 서유럽 인코딩으로 읽은 경우)에서는 **96.8%로 거의 완벽하고**, 그 안에서는 우리보다 정교한 처리도 한다(다중 중첩 깨짐, 둥근 따옴표가 덧씌워진 경우, U+A0 소실 등).

> 이전 문서에는 이 구간이 68.0%로 적혀 있었다. 구간을 "cp1252·latin-1 오독"으로 잡았는데 그 안에 EUC-KR·GBK·Big5 원문이 섞여 들어가 ftfy 점수가 부당하게 낮게 나왔다. 위 표는 UTF-8 원문만으로 다시 잡은 값이다.

반면 CJK 인코딩이 얽힌 깨짐 — 한국에서 "뷁체"라 부르는 그것 — 은 ftfy의 대상 밖이고, **71건 중 0건**이다. 같은 구간에서 이 도구는 UTF-8→EUC-KR 오독 20건을 100% 복구한다. `Za탉처흢훶`, `d챕j횪` 같은 CP949 오독을 그대로 반환한다. 키릴 오독도 15.4%에 그친다.

**이 도구의 존재 이유가 여기 있다.** CJK·키릴 사용자가 겪는 깨짐은 표준 도구의 사각지대다. 반대로 ftfy 주력 구간에서 우리가 이겼다고 주장할 근거는 없다 — 31건 100% 대 96.8%는 표본이 작아 사실상 동률로 보는 게 맞다.

실무적으로도 대체 불가능하다. ftfy는 Python이라 브라우저에서 못 돈다. Pyodide 포팅이 있으나 WebAssembly 위에서 Python 런타임을 돌리는 구조라 원본보다 4배 느리고, 런타임을 통째로 받아와야 해서 40KB짜리 도구에는 맞지 않는다.

### ftfy에서 가져올 아이디어

- **둥근 따옴표 정규화** — 깨진 텍스트가 메신저나 워드를 거치며 `'`가 `'`로 바뀌면 바이트 복원이 실패한다. 되돌리기 전 정규화를 넣으면 잡히는 케이스가 있다.
- **부분 깨짐 처리** — 문장 일부만 깨진 경우. 현재는 전체를 한 덩어리로 채점해서 멀쩡한 부분이 섞이면 점수가 흐려진다.

### 우선순위 1 — 다국어 (i18n)

**엔진은 이미 다국어인데 UI가 한국어에 묶여 있다.** 벤치마크가 12개 언어에서 90%+를 내는데, 정작 한국인만 쓸 수 있는 상태다. 이 도구의 차별점이 "ftfy가 못 고치는 CJK 깨짐"인데 일본·중국 사용자가 도달할 수단이 없다.

막혀 있는 것:

| 항목 | 현재 |
|---|---|
| `<html lang>` | `ko` 고정 — 검색엔진이 한국어 페이지로만 색인 |
| `<title>` / `description` | 한국어 고정 — `文字化け 直す` 검색에 안 걸림 |
| UI 문자열 | 25개 하드코딩 (버튼, 에러, 결과 라벨) |
| 본문 설명 | 51줄 한국어 고정 |

구조 변경은 불필요하다. 문자열만 분리하면 된다.

```js
const I18N = {
  ko: { title: '깨진 글자 복구기', go: '복구하기', copy: '복사', ... },
  ja: { title: '文字化け修復ツール', go: '修復する', copy: 'コピー', ... },
  en: { ... }
};
```

**작업 순서**

1. UI 문자열 25개를 `I18N` 객체로 추출, `ko` 먼저 채우고 동작 확인
2. 본문 설명 텍스트도 동일하게 분리
3. `<html lang>` 과 메타태그를 언어에 따라 설정
4. `ja` → `en` → `zh` → `ru` 순으로 번역 추가
5. 언어 전환 UI (헤더 우측)

**주의:** 번역 대상은 UI와 본문뿐이다. 기계번역 결과를 검수 없이 넣으면 저품질 콘텐츠로 판정될 위험이 있다.

언어 전환 UI를 붙일 때, **입력창 우측 상단은 피할 것.** 예전에 그 자리에 예시 로더 버튼(`한국어` `일본어` …)을 뒀다가 언어 전환기로 오인돼 걷어냈다. 헤더 우측이 맞는 자리다.
