## 1. 목표

인코딩 불일치로 깨진 텍스트를 브라우저에서 복구해주는 도구 사이트. 애드센스 승인을 통과하고 검색 유입으로 광고 수익을 만드는 것이 목적.

**성공 지표**

| 단계 | 지표 | 목표 |
|---|---|---|
| 1차 | 애드센스 승인 | 신청 후 2주 내 |
| 2차 | 월 세션 | 3개월 내 5,000 |
| 3차 | 월 세션 | 12개월 내 50,000 |

**비목표 (하지 않는 것)**

- 로그인·계정·저장 기능
- 서버 사이드 처리 (텍스트는 전량 클라이언트에서 처리)
- 앱 출시

## 2. 참고 모델

`base64decode.org` 계열의 단일 목적 도구 사이트 패턴을 따른다.

**핵심 특징 3가지**

1. **도구가 최상단.** 스크롤 없이 바로 쓸 수 있음. 사용자는 "복구"만 하고 떠나도 됨
2. **본문이 같은 페이지에 붙음.** 별도 블로그 없음. 도구 아래로 개요 → 사용법 → 원리 → FAQ가 이어짐
3. **다국어 하위 디렉토리.** 같은 도구를 언어별 경로로 복제. 엔진은 공유, 문자열과 본문만 번역

**우리가 안 따라가는 것**

- 자매 도메인 분리 운영 (도메인 관리 비용 대비 이득 없음, 단일 도메인 하위 경로로)
- 파일 업로드 서버 처리 (`[미정]` — 3장 참고)

## 2.5 경쟁 도구 분석 — ftfy

[ftfy](https://github.com/rspeer/python-ftfy)는 mojibake 복구의 사실상 표준 라이브러리다. 동일 벤치마크(148건, 12개 언어)로 측정:

| 구간 | n | ftfy 6.3.1 | 이 도구 |
|---|---|---|---|
| 전체 | 148 | 24.3% | **84.5%** |
| UTF-8 → 서구권 오독 (ftfy 주력) | 31 | **96.8%** | 100% |
| CJK 인코딩으로 오독 | 20 | **0.0%** | **100%** |
| 키릴 인코딩으로 오독 | 39 | 15.4% | **97.4%** |
| CJK 원문이 깨진 경우 | 51 | **0.0%** | **66.7%** |

ftfy는 영어권 웹의 `â€™` 계열(UTF-8 → 서유럽 인코딩)을 정조준한 도구다. **그 영역에선 96.8%로 거의 완벽하고**, 우리보다 정교하기까지 하다 — 다중 중첩 깨짐, 둥근 따옴표가 덧씌워진 경우, U+A0 소실까지 처리한다. 주력 구간에서 우리가 이겼다고 주장할 근거는 없다(31건 100% vs 96.8%는 사실상 동률).

**그러나 CJK 인코딩이 얽힌 깨짐(한국에서 말하는 "뷁체")은 대상 밖이다 — 71건 중 0건.** 같은 구간에서 이 도구는 UTF-8→EUC-KR 오독 20건을 100% 복구한다. `Za탉처흢훶`, `d챕j횪` 같은 결과를 그대로 반환한다. 키릴 오독도 15.4%에 그친다.

### 전략적 함의

1. **포지셔닝이 명확해졌다** — "CJK 사용자를 위한 mojibake 복구기". ftfy가 있는데 왜 만드냐는 질문에 숫자로 답할 수 있다.
2. **다국어 우선순위를 M4 → M2로 올린다** — 차별점이 CJK인데 현재 UI가 한국어 전용이라 일본·중국 사용자가 도달할 수단이 없다. 모순 상태.
3. **콘텐츠 소재가 생겼다** — "ftfy로 안 고쳐지는 한글 깨짐" 은 그 자체로 검색 유입이 되는 주제다. 벤치마크 표를 본문에 그대로 쓸 수 있다.

기술적 대체 가능성은 없다. ftfy는 Python이고, Pyodide 포팅은 WebAssembly 위에서 Python 런타임을 돌려 원본보다 4배 느리다. 40KB 도구에 런타임을 통째로 얹을 수는 없다.

## 3. 정보 구조

### 3.1 URL 설계

```
/                        메인 — 깨진 글자 복구기
/csv.html                CSV·엑셀 한글 깨짐 복구
/detect.html             인코딩 판별기
/convert.html            EUC-KR ↔ UTF-8 변환기

/about.html              사이트 소개
/privacy.html            개인정보처리방침   [애드센스 필수]
/terms.html              이용약관
/contact.html            문의

/ja/index.html …         위 구조 전체를 언어별 폴더로 복제
```

한국어를 루트에 두고 나머지를 언어별 폴더로. 각 페이지에 `hreflang` 상호 링크 필수.

> **갱신 (20차) — 주소가 `mojibake.prelaps.com` 이 됐다.**
>
> `prelaps.com` 은 이 도구 전용이 아니라 **우산 브랜드**다. 게임·유틸리티처럼 성격이 전혀 다른 것들이 그 아래 들어온다. 그래서 각자 서브도메인을 갖고, 이 저장소는 `mojibake` 하나다. 루트는 나중에 만들 랜딩이 가져간다.
>
> **하위 경로(`prelaps.com/mojibake`)를 검토했다가 기각했다.** 저장소가 도구마다 갈리므로 하위 경로로 가려면 Worker 라우팅 + 법적 페이지 이사 + `test/links.js` 수정이 딸려온다. 그 값을 치르고 얻는 것은 "신뢰도가 한 도메인에 모인다" 인데, **그 이득은 주제가 이어질 때만 나온다** — 게임과 텍스트 도구는 검색 사용자가 겹치지 않아 거의 안 모인다.
>
> **약관 복제 걱정도 여기서 풀린다.** 도메인 공용 법적 페이지를 고집했던 것은 도구가 전부 비슷한 텍스트 도구라는 전제 때문이었다. 게임은 점수를 저장할 수도 있고 이 도구는 아무것도 안 받으므로 **개인정보처리방침이 원래 달라야 한다.** 복제가 아니라 각자 맞는 문서다.
>
> - 15장의 `canonical`·`hreflang`·`og:url`·`og:image` + `sitemap.xml` + `robots.txt` + `test/links.js` 의 `ORIGIN` 을 전부 교체했다
> - 법적 페이지 본문의 적용 범위도 `Prelaps(mojibake.prelaps.com)` 로 좁혔다
> - 배포는 Cloudflare Pages 가 아니라 **Workers + Static Assets** 다 (`wrangler.jsonc`). Pages 가 Workers 로 합쳐지는 중이라 신규 프로젝트는 이쪽이다

> **갱신 (19차) — 허브를 지우고 도구를 루트로 되돌렸다.**
>
> 아래 18차 상자는 "도메인을 여러 도구가 나눠 쓴다" 는 전제 위에 서 있었다. **그 전제가 취소됐다** — 도구를 모으는 허브는 이 저장소가 아니라 다른 곳에서 만들기로 했고, 여기는 깨진 글자 복구기 전용이다.
>
> ```
> /                       깨진 글자 복구기        index.html
> /content/{about,privacy,terms,contact}
> /en/ · /ja/             위 구조를 언어별로 그대로
> ```
>
> - **허브 3장을 지워 18장 → 15장.** 도구가 하나뿐인 상태에서 허브는 한 칸짜리 목차라, 주소를 직접 친 사람에게 클릭 한 번을 더 받을 뿐이었다.
> - **되돌리는 비용이 0 인 시점이라 지금 했다.** 배포 전이라 색인이 하나도 없었다. 배포 후에 같은 판단을 하면 `/mojibake` 에 쌓인 색인을 버리게 된다.
> - **`hreflang`·`canonical`·`og:url`·`sitemap.xml` 이 전부 따라 바뀌었다.** `/mojibake` → `/`, `/en/mojibake` → `/en/`. `test/links.js` 가 15장 기준으로 통과한다.
> - **법적 페이지의 적용 범위 문장은 그대로 뒀다** — 사이트 이름 기준이라 도구 구성이 바뀌어도 틀리지 않는다.
> - 18차 상자는 지우지 않고 남긴다. 도구를 더 붙일 때 다시 필요해질 설계이고, **그때 치를 값(색인 재구축)** 을 같이 읽어야 하기 때문이다.

> **갱신 (18차) — 도메인이 `prelaps.com` 으로 정해졌고, 위 설계가 두 군데 바뀌었다.**
>
> 도메인을 **여러 도구가 나눠 쓴다.** 인코딩 계열만 늘어나는 것이 아니라 무관한 도구도 들어온다. 그래서 ① **루트가 도구가 아니라 허브(도구 목록)** 가 되고 ② **깨진 글자 복구기는 `/mojibake` 로 내려간다.** 색인이 아직 하나도 안 잡힌 시점이라 이전 비용이 0 이어서 지금 옮겼다.
>
> ```
> /                       허브 — 도구 목록            index.html
> /mojibake               깨진 글자 복구기            mojibake.html
> /mojibake-csv           (M4) 계열은 접두어를 붙인다
> /<무관한도구>             접두어 없이
> /content/{about,privacy,terms,contact}   법적 4장 — 도메인 전체 공용
> /en/ · /ja/             위 구조를 언어별로 그대로
> ```
>
> - **언어가 첫 칸, 도구가 두 번째 칸이다.** 반대로 하면(`/mojibake/en/`) `hreflang` 세트와 사이트맵이 도구 수만큼 쪼개지고, 언어 전환기가 페이지마다 폭발한다.
> - **법적 페이지는 도구별로 복제하지 않는다.** 12장이 도메인 전체를 덮으므로 도구가 늘어도 여기는 안 늘어난다. 대신 약관·개인정보처리방침의 **적용 범위 문장을 도구 이름에서 사이트 이름으로 바꿨다** — 안 바꾸면 두 번째 도구를 안 덮는다.
> - **파일식은 그대로 유지한다.** 위 상자의 이유(더블클릭)에 하나가 더 붙었다 — 파일식이면 **경로 깊이가 2 로 고정되어 푸터가 6종으로 유지된다**(6.1 참고). 폴더식으로 가면 깊이 3 이 생겨 9종이 된다.
> - **배포 URL 에는 확장자가 없다.** Cloudflare Pages·Netlify 가 `.html` 을 떼고 301 한다. 내부 링크는 더블클릭 원칙 때문에 `.html` 을 유지하고, `canonical`·`og:url`·`sitemap.xml` 만 확장자 없는 최종 URL 로 쓴다. 둘의 형태가 다른 것은 실수가 아니라 이 원칙의 대가다.
> - **`hreflang`·`canonical`·`og:image`·`sitemap.xml` 을 18장 전부에 넣었다.** 도메인 대기로 미뤄뒀던 항목이 이 시점에 한꺼번에 풀렸다. `x-default` 는 `/en/` 계열이다 — 언어가 안 맞는 방문자를 보낼 곳이라 영어가 맞고, 한국어가 루트인 것과는 별개다.
> - **`test/links.js` 가 이걸 전부 검사한다.** 존재 검사만으로는 부족하다 — 영어 페이지 푸터가 한국어 약관을 가리켜도 브라우저는 멀쩡히 연다. `npm run check:links`.

> **폴더식(`/about/`)이 아니라 파일식(`/about.html`)이다 — 되돌리지 말 것.**
> 폴더식으로 하면 웹서버가 `/about/` 을 `/about/index.html` 로 바꿔줘야 한다. 그래서 빌드 결과를 그냥 더블클릭으로 열면 링크가 전부 죽고, 확인하려고 매번 로컬 서버를 띄워야 한다. zip 으로 넘기거나 USB 에 담아도 안 열린다.
> **구글은 두 방식을 동일하게 색인하므로 SEO 손해가 없다.** 주소가 조금 덜 깔끔한 것과 "서버 없이 열린다" 를 맞바꾼 것이고, 후자가 훨씬 실용적이었다.

### 3.2 페이지별 차별화 (doorway page 회피)

같은 템플릿에 키워드만 바꾸면 구글이 doorway page로 판정한다. **각 페이지는 도구 동작 자체가 달라야 한다.**

| 경로 | 도구 차이 | 타겟 검색어 |
|---|---|---|
| `/` | 텍스트 붙여넣기 → 후보 3개 제시 | 한글 깨짐, 글자 깨짐 복구 |
| `/csv.html` | 파일 드롭 → BOM 감지 → 수정본 다운로드 | 엑셀 csv 한글 깨짐 |
| `/detect.html` | 복구 없이 인코딩 추정 결과만 표시 | 인코딩 확인, 파일 인코딩 |
| `/convert.html` | 방향 지정 변환 (자동 판별 없음) | euc-kr utf-8 변환 |

`/csv.html`는 파일을 다루지만 `FileReader`로 클라이언트에서 처리 가능 — 서버 불필요.

> **현황 (9차)** — 파일 처리 기능은 이미 만들어져 `/` 안의 **탭**으로 붙어 있다(5.1.3). 빌드 구조가 없어 페이지를 나눌 수 없었기 때문이다. 로직은 독립 함수(`recoverBytes` / `zipInspect` / `zipRebuild`)라 나중에 `/csv.html` 로 그대로 옮길 수 있다. 그때까지는 `/csv.html` 검색어 유입을 못 잡는다는 점을 감수한다.
>
> ZIP 파일명 복구는 원래 URL 설계에 없던 도구다. 검색어("압축 파일 한글 깨짐", "zip 파일명 깨짐")가 별도로 존재하므로 M4 에서 `/zip.html` 을 추가 후보로 둔다.

## 4. 페이지 템플릿

모든 도구 페이지가 공유하는 섹션 순서.

```
① 헤더 (로고 / 도구 메뉴 / 언어 전환)
② H1 + 한 줄 설명
③ ★ 도구 본체            ← 스크롤 없이 보여야 함
④ 결과 영역
──────────────────────
⑤ [광고 A]               결과 아래
⑥ 개요 — 이 도구가 뭘 하는지
⑦ 사용법 — 옵션·예시 설명
⑧ [광고 B]               본문 중간
⑨ 원리 — 왜 깨지는지, 어떻게 되돌리는지 (예제 테이블 포함)
⑩ 안 될 때 — 복구 불가 케이스
⑪ FAQ
⑫ 관련 도구 링크
⑬ [광고 C]               푸터 위
⑭ 푸터 (About / Privacy / Terms / Contact / 저작권)
```

**본문 분량 기준:** 페이지당 1,500자 이상. 이게 애드센스 승인의 핵심 변수.

**광고 관련 제약**

- 광고는 3개까지. 본문 분량이 광고보다 많아야 함
- `복구하기` 버튼 반경에 광고 금지 (오클릭 유도 = 계정 정지)
- 모든 광고 슬롯은 `min-height` 사전 지정 (CLS 방지)
- 결과가 동적으로 갱신되는 컨테이너 **안에** 광고 배치 금지

## 5. 기능 명세

### 5.1 복구 엔진 (기존 코드 유지)

현재 `text.html`의 로직을 그대로 모듈화. 재작성 불필요.

**입력** 깨진 문자열
**출력** 후보 배열 (최대 3개) — 각 항목: `{ 결과문자열, 잘못읽은인코딩, 실제인코딩, 점수 }`

**처리 흐름**

1. 입력 문자 성격 분석 → "잘못 읽은 인코딩" 후보 압축 (`narrowMisread`)
2. 각 후보로 역인코딩 → 원본 바이트 복원 (`encodeWith`)
3. 복원된 바이트를 실제 인코딩 후보 20종으로 디코딩
4. 문자 분포 기반 점수화 (`score`) → 상위 3개 반환

**모듈 분리안**

```
src/engine/
  ├─ spec.js        인코딩 정의 테이블
  ├─ encoder.js     역변환 테이블 생성 + 캐시
  ├─ scorer.js      문자 분류 및 채점
  └─ recover.js     엔트리포인트
```

### 5.1.1 정확도 벤치마크

> **현재 값 (148건, 실사용 기준 = 브라우저): 1순위 84.5% / 후보 3개 내 96.6% / 평균 2.3ms.**
> Node 벤치마크는 82.4% / 86.5% 로 더 낮게 나오는데, Node(ICU)와 브라우저(WHATWG index)의 `TextDecoder` 인코딩 표가 다르기 때문이다(euc-kr 기준 8,412 vs 17,048쌍). 사용자가 쓰는 건 브라우저이므로 브라우저 숫자를 기준으로 삼는다. 6차 항목 참고.

6개 언어 × 12가지 깨짐 패턴으로 측정. 이론상 복구 불가능한 케이스(인코딩 단계에서 바이트가 이미 소실된 경우)는 제외하고 유효 47케이스.

**원인** — 채점 함수의 배점 불균형. 스크립트(한글·가나·한자·키릴)는 110점, 악센트 문자(é, ü, ß)는 55점. 라틴 언어의 정답은 대부분 ASCII + 악센트 소수라서, 키릴로 오독된 오답에게 구조적으로 밀린다.

**수정 내용 (2줄)**

```js
// 1) attempt() — UTF-8 엄격 검증 보너스
//    UTF-8은 바이트 구조가 엄격해 무작위 바이트가 유효할 확률이 낮다.
//    반면 단일바이트 인코딩은 어떤 바이트든 항상 디코딩에 성공하므로 변별력이 없다.
let strictUtf = false;
if (X === 'utf-8') {
  try { new TextDecoder('utf-8', {fatal:true}).decode(bytes); strictUtf = true; } catch(e) {}
}
// ...
let sc = score(t);
if (strictUtf) sc += 70;

// 2) score() — 악센트 배점을 스크립트와 동등하게
sc += f('accent') * 110;   // 기존 55
```

**3차 수정 — 문자 분류 범위**

`ACCENT` 집합이 서유럽·터키어 문자만 손으로 나열한 것이라, 폴란드어 `ł ż ć ę`, 체코어 `č ř ů`, 헝가리어 `ő ű` 가 `latinodd`(-150점)로 분류돼 정답이 벌점을 받았다. 베트남어 성조 문자는 `rare`(-260점)였다.

```js
if (cp >= 0x100 && cp < 0x180) return 'accent';   // Latin Extended-A
if (cp >= 0x1E00 && cp < 0x1F00) return 'accent'; // Latin Extended Additional (베트남어)
```

**3차까지의 결과** (12개 언어, 유효 76케이스) — *계측 결함 있음, 아래 4차 참고*

**4차 수정 — 계측 결함 (92.1% → 81.1%, 엔진 무수정)**

`benchmark.js` 가 깨짐 생성은 `TextDecoder`, 왕복 검증은 `iconv.encode` 로 서로 다른 인코딩 라벨 체계를 쓰고 있었다. WHATWG 표준에서 `latin1`·`iso-8859-1` 은 **`windows-1252` 의 별칭**이라 진짜 ISO-8859-1 이 아니다. 두 체계가 어긋나는 조합이 왕복 검사에서 전부 조용히 탈락했다.

그 결과 유효 76건의 72%가 키릴·서구권 단일바이트 오독이었고, **`euc-kr` 오독은 0건**이었다. 2.5절이 세운 "CJK 사용자를 위한 mojibake 복구기"라는 포지셔닝의 근거를 정작 측정하지 않고 있었던 셈이다.

라벨을 `iconv-lite` 로 통일하고 멀티바이트→latin1 쌍 7개, CJK 혼합 샘플 2개를 추가해 **유효 76 → 148건**. 정답률이 떨어진 게 아니라 원래 그 값이었다.

**5차 수정 — 길이 축소 신호 (81.1% → 82.4%)**

계측을 고치자 드러난 편향: `score()` 는 문자 종류의 **비율**만 보는데, 2바이트→1바이트 오독은 글자 수가 2배로 불어나 스크립트 비율이 100%에 수렴한다. 반면 정답은 공백·숫자·문장부호(45점)가 섞여 희석된다. 공백이 섞인 현실적인 CJK 문장일수록 오답이 구조적으로 유리했다.

mojibake 복구의 정답은 거의 항상 입력보다 글자 수가 줄어든다. 이 신호를 `attempt()` 에 가점으로 넣었다:

```js
sc += Math.max(0, 1 - t.length / s.length) * 30;
```

배점 조정(`ascii`/`ws`/`punct` 45→75)은 한국어를 100%→90%로 퇴행시켜 기각, 공백 분모 제외는 무변화로 기각했다.

**6차 수정 — 브라우저 실측 도입 + 가짜 답 제거**

엔진은 `TextDecoder` 표를 그대로 신뢰하는데 Node(ICU)와 브라우저(WHATWG index)의 표가 다르다. euc-kr 은 Node 8,412쌍 / Chrome 17,048쌍으로 두 배 차이다. `test/browser.js` 를 추가해 Chrome headless 에서 실제 엔진을 돌리도록 했고, 케이스 정의는 `test/cases.js` 로 분리해 두 러너가 공유한다.

같이 처리한 것:

- `encodeWith` 의 `0x3F`(`?`) 주입 제거 — 바이트가 오염된 후보를 버린다. 정확도 손실 0, `"??"` 같은 가짜 1순위만 사라짐
- 진단 UI — 실패 사유를 `` 소실 / `?` 치환 / 붙여넣기 중 C1 제어문자 소실 / 짧은 입력 으로 구분해 안내
- 10자 미만 입력에서 확신도 % 숨김 (5.1.2 의 "대응" 항목 이행)

**최종 결과** (12개 언어, 유효 148케이스, Chrome 기준)

실패 23건 중 18건은 2·3순위에 정답이 있다. 후보 3개 UI 덕에 체감 실패는 5건(3.4%).

**시도했다가 되돌린 것 — 인코딩 후보 확장**

브라우저 `TextDecoder` 지원 37종을 전부 후보에 넣자 정확도가 **84.2% → 81.6% 로 하락**하고 속도는 50% 느려졌다. 채점이 약한 신호라 후보가 늘면 오답이 정답을 이길 기회가 늘어난다. 되돌리되, 실사용 빈도가 높은 `iso-2022-jp`·`gb18030` 두 개만 유지(총 20종).

### 5.1.2 알려진 한계

**짧은 입력에서 정확도 급락**
채점은 문자 종류의 *비율*만 계산한다. `안녕하세요`와 `똠뷁쨉먄`을 구분하지 못한다 — 둘 다 100% 한글이므로 동점이다. 입력이 10글자 미만이면 통계가 성립하지 않아 사실상 추측이 된다. 실패 케이스가 짧은 샘플(`你好世界` 4자, `Привет` 6자, `שלום עולם`)에 몰려 있다.

**대응**
- 입력 10글자 미만이면 확신도 % 대신 "입력이 짧아 정확도가 떨어집니다" 안내 표시
- `confidences()` 반환값을 짧은 입력에서 그대로 노출하지 않는다 (근거 없는 숫자는 신뢰를 깎는다)

**관측 — 기준선 바로 위에서도 가짜 확신도가 붙는다 (11차)**
잘린 문자열 `¾È³çÇÏ¼¼¿ä…`(11자)를 넣었더니 완전한 오답에 **88% 확신도**가 표시됐다. `SHORT_LEN=10` 을 한 글자 넘겨 확신도 계산이 그대로 돌아간 것이다. 진단 자체는 정상이었다 — "중간에 바이트가 하나 빠진 것 같습니다" 를 띄우고 부분 복구 후보도 냈다. 문제는 **확신도를 가릴지 말지를 글자 수 하나로만 정한다**는 점이다.

임계값을 올리는 것으로는 못 푼다. 정상적인 짧은 입력의 확신도까지 같이 사라진다. 근본 해결은 아래 M6(언어 모델)와 같다 — 짧아도 "이 글자 조합이 그 언어에서 흔한가" 를 볼 수 있으면 확신도에 근거가 생긴다.

**UTF-8 → windows-1252 오독은 절반 이상이 원리적 복구 불가**
cp1252 는 `0x81 0x8D 0x8F 0x90 0x9D` 다섯 자리에 매핑이 없다. UTF-8 바이트가 거기 떨어지면 읽는 순간 소실된다. 한글 음절 11,172자 중 1,760자(15.8%)가 해당하고, 5글자 문장이면 58% 확률로 최소 하나가 죽는다. latin1(진짜 ISO-8859-1)은 256자리가 다 차 있어 이 문제가 없다. 8차에서 UI 안내에 반영. **"왜 어떤 건 되고 어떤 건 안 되나" 는 본문 콘텐츠 소재이기도 하다(4장 ⑩ 안 될 때).**

**부분 복구는 어느 것이 맞는지 판정하지 못한다**
바이트가 빠진 입력에서 `` 앞까지 되살린 후보들은 채점상 전부 동점이다(`안녕하셀` = `照括馬漆` = `救崇窍伎` = 110.0). 한국어가 먼저 표시되는 건 `ACTUAL` 배열 순서 때문이지 판단 결과가 아니다. 구분하려면 언어별 bigram 테이블이 필요하다(M6(언어 모델)).

**붙여넣기 과정의 2차 손상 (도구 밖 문제, 그러나 체감 타율의 최대 변수)**
UTF-8→latin1 계열 깨짐에는 C1 제어문자(U+0080~U+009F)가 섞여 있는데, 메신저·웹 입력창·문서 편집기를 거치면 이 문자가 조용히 사라지거나 리터럴 텍스트로 바뀐다. 그러면 바이트가 소실돼 원리적으로 복구 불가가 된다. 엔진으로는 못 고치므로 6차에서 UI 안내로 대응했다.

> **같은 경로의 NBSP 손상은 되살릴 수 있다 (15차, 5.1.7).** 여기 적힌 "복구 불가"는 **C1 에 대한 것**이다. NBSP(U+00A0)도 같은 경로에서 일반 공백으로 바뀌지만, UTF-8 구조가 원래 바이트를 확정해주므로 복원된다(148건 중 20건이 이 경우였고 전부 실패하던 것을 100% 회복). 둘을 한 덩어리로 취급하지 말 것.

**멀티바이트 → 단일바이트 오독의 1순위 정확도**
남은 실패 23건 중 18건이 이 유형(`shift_jis→latin1`, `gbk→latin1`, `big5→latin1`)이다. 정답은 후보 안에 있는데 1순위를 못 잡는다. 5차의 길이 축소 신호가 방향은 맞지만 충분히 강하지 않다는 뜻이다.

**근본 해결 (M6(언어 모델)로 유예)**
언어별 bigram 빈도 테이블 도입. `안녕`은 한국어에서 흔하고 `똠뷁`은 아니라는 걸 구분할 수 있다. 단점은 테이블 확보 비용과 번들 증가. 현재 84.5% + 후보 3개 제시 UI(96.6%)로 당장은 넘어간다고 판단, 우선순위 낮춤. 실패 케이스가 짧은 샘플에 몰려 있어 이 항목의 잠재 이득은 이전 추정보다 크다.

> **용량 추정은 "언어당 수십 KB" 였는데 과대평가였다 (15차).** Firefox 의 `chardetng` 는 풀 n-gram 이 아니라 **거칠게 분류한 문자의 "쌍" 빈도**로 30개 인코딩을 **62KB** 에 담는다. 6.3 의 JS 예산 여유가 약 6KB 이므로 한국어·일본어로 좁히면 들어갈 여지가 있다. 미뤄둔 근거가 약해졌다는 뜻이라, 다시 검토할 때 이 문장을 볼 것.

**원리적 복구 불가 케이스 (도구 문제 아님)**
- `?`, `` 로 치환된 문자 — 바이트 자체가 소실됨
- 저장 대상 인코딩이 해당 문자를 표현할 수 없었던 경우 (예: 한글을 shift_jis로 저장)
- 이 경우 UI에서 "복구 불가" 사유를 명시할 것

### 5.1.3 파일 모드 (9차)

붙여넣기 입력에는 구조적 손실이 있다. 엔진은 깨진 *문자열*에서 `encodeWith` 로 원본 바이트를 **역추정**하는데, 그 인코딩으로 만들어질 수 없는 글자가 하나라도 있으면 후보가 통째로 탈락한다. 게다가 5.1.2가 "체감 타율의 최대 변수"로 지목한 C1 제어문자 소실이 바로 이 경로에서 일어난다.

파일은 원본 바이트를 그대로 갖고 있어 **역추정 단계 자체가 없다.** `recoverBytes()` 는 `attempt()` 를 우회해 파일 바이트를 `ACTUAL` 20종으로 바로 디코딩하고, 채점은 `score()` 를 그대로 공유한다.

입력 UI 는 한 페이지 안의 탭 두 개(`붙여넣기` / `파일`)로 붙였다. 파일 모드 로직은 독립 함수라 M1 에서 빌드 스크립트를 도입할 때 `/csv.html` 로 그대로 옮길 수 있다.

**측정 결과** (12개 언어 × 19개 인코딩, 유효 77건)

| | 1순위 | 후보 3개 내 | 평균 |
|---|---|---|---|
| Node | 76.6% | 81.8% | 0.4ms |
| **Chrome (실사용)** | **75.3%** | **88.3%** | 0.2ms |

붙여넣기 84.5% 보다 낮아 보이지만 **케이스 집합이 달라 직접 비교하면 안 된다.** 파일 벤치는 단일바이트 인코딩 12종을 동등 비중으로 재는데, 그 구간이 아래 설명하는 원리적 동점이라 전체 숫자를 끌어내린다. 같은 CJK 구간만 보면 utf-8 20/20, euc-kr 7/7, gbk 8/8 로 100% 다.

**단일바이트끼리는 원리적으로 동점이다**

`score()` 는 문자 *종류*의 비율만 본다. 그래서 같은 바이트를 그리스어로 읽든 키릴로 읽든 라틴 악센트로 읽든 전부 스크립트 110점이라 **완전 동점**이 난다:

```
Καλημέρα κόσμε / КблзмЭсб кьуме / ÊáëçìÝñá êüóìå  →  셋 다 105.4
```

붙여넣기 모드는 `narrowMisread` + `encodeWith` 가 후보를 걸러 이 문제가 드러나지 않는다. 파일 모드는 바이트를 그대로 쓰므로 단일바이트 12종이 한꺼번에 동점으로 남는다. 5.1.2 의 "짧은 입력" 한계와 같은 뿌리이고, 같은 해법(M6(언어 모델))이 필요하다.

동점을 배열 순서로 깨면 windows-1251 이 항상 이겨 서유럽 파일이 전부 키릴로 나온다. 실사용 빈도를 최대 6점짜리 사전 확률(`FILE_PRIOR`)로 준다 — `score()` 의 신호 차이는 보통 45점 단위라 근거가 있을 때는 뒤집지 못한다. **66.2% → 76.6%, 독일어·프랑스어 29·40% → 100%.**

**시도했다가 되돌린 것**

- **길이 축소 가점(5차)의 이식** — 브라우저 68.8%로 떨어졌다(제거 시 75.3%, 독일어 29% → 100%). 그 가점은 "입력이 이미 깨진 것이 확실할 때 정답은 짧다"는 전제인데 파일에는 그 전제가 없다. 오히려 단일바이트 파일을 아무 CJK 인코딩으로 읽으면 글자 수가 반이 돼 가점을 챙긴다. Chrome 은 euc-kr 을 Node 의 두 배로 매핑해 이 오답이 훨씬 잘 살아남는다.
- **인코딩 후보 확장** — `windows-874`·`iso-8859-8`·`windows-1258`·`iso-8859-5` 추가는 1순위·3개내 **둘 다 무변화**. 붙여넣기 모드의 결론(5.1.1 6차)이 파일 모드에서도 그대로다.

**가드 (후보 경쟁을 아예 돌리지 않는 경우)**

| 조건 | 판정 |
|---|---|
| BOM(`EF BB BF` / `FF FE` / `FE FF`) | 인코딩이 파일에 명시됨 — 깨질 이유 없음 |
| NUL 바이트 또는 제어문자 5% 초과 | 이진 파일 — 인코딩 불일치라는 개념이 없음 |
| 0x80 이상 바이트 없음 | 순수 ASCII — 불일치가 성립 불가 |
| 20MB 초과 | 거부 (9장 미결정 2번에 대한 답) |

**엑셀 CSV 대응** — 내려받을 때 UTF-8 BOM 을 붙이는 옵션을 둔다(`.csv`/`.tsv`/`.txt` 는 기본 켜짐). 엑셀은 BOM 없는 UTF-8 CSV 를 로컬 코드페이지로 읽어 **다시 깨뜨리므로**, "엑셀 csv 한글 깨짐" 검색어의 실제 해결책은 인코딩 판별이 아니라 이쪽이다.

**ZIP 파일명 복구** — ZIP 은 파일명 인코딩 플래그(GP bit 11)가 없으면 로컬 코드페이지로 저장된다. 한국 윈도우에서 만든 압축 파일이 다른 환경에서 깨지는 원인이다. 파일명을 **전부 이어붙여 한 덩어리로 판별**하고(이름 하나는 짧아 통계가 안 선다), 압축 데이터는 그대로 복사한 채 헤더만 새 이름 + bit 11 로 다시 쓴다. **inflate/deflate 가 필요 없어 외부 라이브러리 의존성이 0 이다.** ZIP64·암호화·분할 아카이브는 감지해서 거부한다.

### 5.1.4 "깨진 파일" vs "내용이 깨진 파일" (10차)

파일 탭을 실사용해보니 곧바로 드러난 구멍. 사용자는 깨진 글자를 어디선가 복사해 **메모장에 저장해서 올린다.** 그 파일은 깨진 파일이 아니다 — 바이트는 정상 UTF-8 이고 담긴 *글자*만 mojibake 다.

| | 깨진 파일 | 내용이 깨진 파일 |
|---|---|---|
| 상태 | 바이트가 euc-kr 인데 utf-8 로 읽힘 | 바이트는 정상 utf-8, 글자가 이미 mojibake |
| 어떻게 생기나 | 옛날 프로그램이 저장 | 깨진 글자를 복사해 저장 |
| 빈도 | 낮음 | **높음 (도구를 찾아오는 경로 자체가 이것)** |

**결함 두 개가 겹쳐 있었다**

1. `recoverBytes` 가 인코딩부터 틀렸다. `¾È³çÇÏ¼¼¿ä` 가 담긴 UTF-8 파일이 **gbk 로 판정**돼 `戮脠鲁莽脟脧...` 을 냈다. 깨진 글자는 라틴 보조 문자뿐이라 `score()` 가 낮게 주는데, 같은 바이트를 GBK 로 읽으면 한자가 나와 110점을 받는다. `strictUtf` 가점 +70 으로는 못 막는다.
2. utf-8 을 맞게 골라도 거기서 멈췄다. "정상 파일입니다" 라고 답하고 끝나 아무 쓸모가 없었다.

**수정** — 둘 다 같은 체인으로 풀린다.

- **유효 UTF-8 은 경쟁시키지 않고 확정한다.** 임의의 레거시 바이트가 UTF-8 구조를 우연히 만족할 확률은 극히 낮다 — 파일 벤치의 비 UTF-8 케이스 57건 중 유효 UTF-8 인 것은 **0건**이라 기존 정확도를 하나도 건드리지 않는다.
- **확정된 텍스트를 붙여넣기 모드로 한 번 더 돌린다.** `recover()` 를 그대로 재사용하며 새 로직이 없다.

**`CONTENT_GAIN=25`** — `recover()` 의 개선폭이 이보다 크면 내용이 깨진 것으로 본다.

| 구분 | n | 개선폭 (최소/중앙/최대) |
|---|---|---|
| 정상 텍스트 | 20 | -999 / 0 / **20** |
| 깨진 텍스트 | 148 | -999 / 148 / 403 |

- `> 25` 에서 **감지 137/148, 오탐 0/20**
- `> 10` 은 오탐 8/20 이라 못 쓴다 (정상 한국어·일본어가 15~20을 받는다)
- 놓치는 11건은 대부분 키릴·그리스어 **동점 계열**이다. `Ñåãîäíÿøíåå`(라틴 악센트 110점)와 `Сегодняшнее`(키릴 110점)는 개선폭이 0이라 어떤 임계값으로도 못 잡는다. 5.1.3 의 단일바이트 동점과 같은 뿌리이고 같은 해법(M6(언어 모델))이 필요하다

**섞인 파일은 원리적으로 복구 불가**

서로 다른 방식으로 깨진 글자가 한 파일에 있으면 되돌릴 수 없다. 복구는 "어떻게 잘못 읽혔는지" **하나**를 가정하고 되감는 것이라, 가정이 여러 개면 `encodeWith` 가 전부 null 을 낸다. 고칠 대상이 아니라 안내할 대상이라 `MOJI_HINT=0.5` 로 사유를 표시한다 — 이 값은 결과를 바꾸지 않고 안내 문구만 고른다.

### 5.1.5 줄마다 다르게 깨진 입력 (13차)

예시 4줄을 한꺼번에 붙여넣자 전부 키릴 쓰레기가 나왔다. **줄 수가 문제가 아니었다.**

| 입력 | 결과 |
|---|---|
| 1~3줄 (같은 유형 `euc-kr→latin1`) | 전부 정답 |
| 1~4줄 (4번째만 `utf-8→cp1252`) | 전부 깨짐 |
| 4줄만 | 정답 |

같은 유형이면 여러 줄이 **오히려 더 정확하다**. 무너지는 건 유형이 섞였을 때다. 4번째 줄의 `•…š` 를 `latin1-raw` 가 표현하지 못해 그 가설이 통째로 탈락하고, 4줄 모두를 커버하는 유일한 방식(`windows-1252`)으로 밀려나기 때문이다.

**`recoverLines()`** — 줄마다 `recover()` 를 돌려 이어붙이고, 그 결과가 통짜보다 자연스러울 때만 채택한다(`LINE_GAIN=10`). 새 채점 로직이 없고 기존 `recover()` 를 그대로 재사용한다.

| | n | 통짜 | 적용 후 |
|---|---|---|---|
| 한 언어·한 유형 문단 | 23 | 21 | **21** (발동 0건) |
| 유형 섞인 입력 | 228 | 3 (1%) | **60 (26%)** |

**정상 문단에서는 규칙이 아예 발동하지 않는다.** 줄별 결과가 통짜보다 점수가 높게 나오는 일 자체가 없어서, 임계값을 0~40 무엇으로 잡아도 개악이 0이다.

결과는 랭킹에 섞지 않고 전용 카드로 위에 둔다 — 줄마다 근거가 달라 카드 형식에 안 맞고, 부분 복구와 같은 원칙이다. 대신 이 카드가 뜨면 **랭킹의 확신도를 `참고용` 으로 낮춘다.** 통짜 1순위가 쓰레기인데 88% 가 붙던 것이 이 문제의 체감상 핵심이었다.

### 5.1.6 정상 글자가 섞인 입력 (14차)

벤치마크 148건은 **깨진 글자만 딱 떼어낸 합성 입력**이다. 실사용자는 그렇게 가져오지 않는다. 같은 148건에 현실적인 맥락만 붙여 다시 쟀다.

| 입력 형태 | 1순위 정답 | 후보 0개 |
|---|---|---|
| 통짜 — 벤치마크가 재던 것 | 82.4% | 3.4% |
| 앞에 한글 라벨 `"제목: "` | **0.0%** | 98.0% |
| 뒤에 한글 `" 확인바람"` | **0.0%** | 98.0% |
| 뒤에 이모지 `" 🙂"` | **0.0%** | 100.0% |
| 파일명 `"_보고서.xlsx"` | **0.0%** | 98.0% |
| 앞에 ASCII 라벨 `"name: "` | 76.4% | 3.4% |

**ASCII 만 멀쩡한 것이 원인을 그대로 말해준다** — `latin1-raw` 가 ASCII 는 표현할 수 있기 때문이다. `encodeWith()` 는 되돌릴 인코딩으로 표현 불가한 문자가 **하나라도** 있으면 그 가설을 통째로 버린다(6차에서 `0x3F` 주입을 없앤 것의 반대편 극단). 정상 한글 한 글자, 이모지 하나면 후보가 전멸한다.

`recoverSegments()` — 되돌릴 수 있는 구간만 골라 되돌리고 나머지는 손대지 않는다. 5.1.5 의 `recoverLines` 를 한 단계 아래로 내린 것이고, 새 채점 로직 없이 `recover()` 를 재사용한다.

| | 통짜 | 구간 복구까지 |
|---|---|---|
| Node | 15.3% | **65.7%** |
| **Chrome (실사용)** | 15.9% | **65.4%** |

통짜 148건은 **82.4% / 84.5% 무변화**다. 통짜 입력은 전체가 한 구간이 되어 발동 조건이 성립하지 않는다. 정상 문장 24건에서도 **발동 0건**이다.

**설계상 지킨 것 셋**

- **구간 분리에 `narrowMisread(s)` 를 쓰면 안 된다.** 입력 *전체*를 보고 후보를 좁히는 함수라, 정상 한글이 섞였다는 이유로 `latin1-raw` 를 빼버린다 — 정작 깨진 구간을 되돌릴 유일한 가설이 그것인데도.
- **개선폭은 양쪽 다 raw `score()` 로 잰다.** `recover().list[0].score` 에는 `attempt()` 의 `strictUtf` +70 과 길이 축소 가점이 섞여 있어, 그대로 비교하면 정상 ` 입니다` 가 gain 197.8 을 받아 교체된다.
- **`SEG_ASCII_MAX=0.6`** — 깨진 글자는 고바이트 문자이고 ASCII 는 어떤 오독을 거쳐도 그대로 통과하므로, ASCII 가 대부분인 구간은 깨진 구간이 아니다. 실측: 정답 구간 278건 최대 0.58(중앙 0.00) / 오작동한 베트남어 `Xin chào b` 0.67.

**시도했다가 되돌린 것 — 공백 단위(토큰) 분할**

커버리지는 더 넓었지만(CJK·키릴 0→53%) 짧은 토큰에서 정상 단어를 깨진 것으로 오판했다 — `déjà vu à côté` → `蹤衪 vu à 饣蹴`. 5.1.2 의 "짧은 입력은 통계가 성립하지 않는다" 가 그대로 재현되는 것이라 임계값으로 못 막는다.

**한 번 잘못 나갔던 것 — 정답 위에 오답 카드 (14차 후속)**

구간 복구를 통짜와 **병행**해서 돌렸더니, 통짜가 이미 정답을 찾은 입력에서도 카드가 떴다. 랭킹 1위는 맞는데 그 위에 쓰레기가 얹히고 확신도까지 참고용으로 강등됐다. 카드가 `.res.best` 라 화면에서 가장 큰 자리다.

**벤치마크가 못 잡은 이유가 핵심이다.** 새 구간을 "통짜가 맞히면 통짜로 세고, 아니면 구간을 시도한다" 로 쟀다. **통짜가 이미 성공했을 때 구간이 끼어드는지를 한 번도 묻지 않았다.** 회귀 감지선으로 넣은 것은 *정상 문장* 뿐이라, *깨졌지만 통짜로 잘 풀리는* 148건이 사각지대였다.

`wholeOk` 가드(통짜가 답을 냈으면 구간을 아예 돌리지 않는다)로 고쳤다. 맥락 정답률 65.7% → 64.9% 를 내주고 회귀를 없앴다. 감지선을 **통짜로 맞힌 케이스 위에 카드 0건** 으로 추가했다.

**같이 드러난 `recoverLines` 의 기존 버그** — 안 깨진 독일어 문단에서 줄별 복구가 발동해 통째로 한자가 됐다(`Bitte prüfen Sie die Unterlagen vorher` → `楂瑴⁥牰曼湥…`). 5.1.5 의 "문단 발동 0건" 검사가 *깨진* 문단만 보고 **안 깨진 문단을 한 번도 안 넣어서** 14차 이전부터 살아 있었다. 같은 ASCII 비율 가드로 고쳤다(임계값은 용도별로 분리 — 구간 0.6 / 줄별 0.65, 범위가 0.65~0.67 에서만 겹쳐 여유가 없다).

**남은 한계** — `제목: <euc-kr로 깨진 한글>` 은 깨진 글자도 한글, 정상 글자도 한글이라 문자 코드만으로는 경계를 못 찾는다. "정상 한글 vs 깨진 한글" 구분이 필요하고 그게 M6(언어 모델)다. 조사 중 확인한 것: Firefox 의 `chardetng` 는 이걸 풀 n-gram 이 아니라 **거칠게 분류한 문자의 "쌍" 빈도**로 하고 30개 인코딩을 **62KB** 로 커버한다. 5.1.2 가 "언어당 수십 KB" 로 추정해 미뤄둔 것보다 훨씬 싸다.

**라이브러리 검토 결과 (같이 조사함)**

`chardet`(22KB, ICU 계열) · `jschardet 4`(gzip 676KB) · `chardetng-wasm` · `ftfy`(Python) 넷 다 **"바이트 → 인코딩 판별" 도구**다. 파일 모드(5.1.3)의 문제는 풀지만 위 표의 문제는 "어디까지가 깨진 구간인가" 라 대상 자체가 다르다. `ftfy` 만 구간 단위로 고치는데 CJK 를 못 한다(2.5절, 71건 중 0건). **이번 건은 라이브러리로 풀 수 있는 문제가 아니었다.**

### 5.1.7 붙여넣다 잃은 NBSP (15차)

5.1.2 는 "붙여넣기 과정의 2차 손상"을 **체감 타율의 최대 변수**로 지목했지만, 다룬 것은 C1 제어문자뿐이었고 그것도 안내 문구로만 대응했다. **NBSP 는 손대지 않았는데, 이쪽은 되살릴 수 있다.**

`제목`(U+C820)처럼 UTF-8 바이트에 `0xA0` 이 든 글자는 latin1 계열로 잘못 읽히면 깨진 문자열에 NBSP(U+00A0)를 남긴다. 그런데 **메신저·HTML·웹 입력창·엑셀이 NBSP 를 일반 공백으로 조용히 바꾼다.**

| | |
|---|---|
| 깨진 결과에 NBSP 가 든 케이스 | **20/148 (14%)** |
| 그중 원래 복구되던 것 | 20건 |
| NBSP 가 공백으로 바뀌면 살아남던 것 | **0건** |
| **복원 후** | **20건 (100%)** — Node·Chrome 동일 |

언어 편중도 없다 — 한국어 4 · 일본어 4 · 중국어 4 · 프랑스어 3 · 베트남어 3 · 태국어 1 · 그리스어 1.

**되살릴 수 있는 이유** — UTF-8 의 이어지는 바이트는 반드시 `0x80~0xBF` 다. `0x20`(공백)은 그 범위에 들 수 없으므로, 그 자리에 공백이 있다는 것 자체가 손상 신호다. 그리고 각 오독 인코딩에서 U+00A0 으로 읽히는 바이트는 하나뿐이라 되돌릴 값이 확정된다. **C1 소실과 성격이 다르다 — 그쪽은 바이트가 진짜로 사라진다.**

**되돌릴 바이트는 인코딩마다 다르다** — latin1·windows-1252·windows-1251 은 `0xA0` 이지만 koi8-r 은 `0x9A`, ibm866 은 `0xFF`, macintosh 는 `0xCA` 다. `0xA0` 으로 고정했다가 `utf-8→koi8-r` 7건이 한 글자씩 틀렸다(`안녕하세젔`, `会議`→`传議`).

오탐은 구조적으로 0이다 — 엄격 UTF-8 검증을 통과할 때만 채택하는데, 정상 텍스트는 애초에 첫 검증을 통과하므로 이 경로에 오지 않는다.

**UI** — 근거 칩에 단계를 하나 더한다(`Latin-1 원시 → 공백 복원 → utf-8`). 감추지 않는 이유는 사용자가 **"다음엔 파일로 올리면 된다"** 를 배우는 자리이기 때문이다. 복구에 성공했으므로 경고가 아니라 안내로 띄운다.

### 5.2 UI 요구사항

- 결과 후보는 순위와 함께 표시, 각각 복사 버튼
- 판별 근거 표시 (`windows-1252로 잘못 읽힌 UTF-8`)
- 실패 시 원인 안내 (`?`나 `` 는 복구 불가임을 명시)
- 바이트가 빠진 입력은 "일부만 되살아난 결과" 를 랭킹 **아래** 별도 섹션에 표시. 순위·확신도는 붙이지 않는다 (어느 것이 맞는지 판정한 게 아니므로)
- 서버 미전송 문구를 눈에 띄게 (신뢰 + 차별점)
- **정상 글자가 섞여 통짜로 못 풀린 경우, 깨진 구간만 되돌린 결과를 전용 카드로 보여준다** (14차, `recoverSegments`). 줄별 복구와 **같은 자리·같은 카드**를 쓴다 — 둘 다 "통짜로는 못 푸는 입력을 쪼개서 풀었다" 는 같은 성격이라 나눌 이유가 없다. **되돌린 부분은 `<mark>` 로 표시한다** — 통짜와 달리 *일부만* 고쳤다는 사실 자체가 사용자에게 정보다
- **후보마다 어느 언어로 읽혔는지 라벨을 붙인다** (12차, `langHint`). 후보 3개를 비교할 때 결과 글자만 보고는 판단이 느리다. 단, **문자로 단정 가능한 것만 언어 이름**을 쓰고 키릴·한자·라틴은 문자 이름으로 물러선다 — 여러 언어가 공유하는 문자에 언어 이름을 붙이면 확신도에서 피해온 근거 없는 단정을 반복하게 된다. 부분 복구 섹션에서는 후보들이 전부 동점이라 이 라벨이 유일한 선택 근거다

**파일 탭 (9차 추가)**

- 입력 방식은 `붙여넣기` / `파일` 탭 두 개. `role="tablist"` + 좌우 화살표 키 이동
- **탭을 바꾸면 반대편 결과를 비운다.** 어느 입력에 대한 답인지 알 수 없게 되므로
- 결과 후보마다 미리보기(앞 500자) + `UTF-8 로 받기` 버튼
- **BOM 붙이기 체크박스** — `.csv`/`.tsv`/`.txt` 는 기본 켜짐. 옆에 이유를 한 줄로 적는다 (엑셀이 BOM 없는 UTF-8 을 다시 깨뜨린다)
- 체크박스 상태는 **누르는 시점에 읽는다.** 결과가 뜬 뒤에도 사용자가 바꿀 수 있다
- 후보 경쟁을 돌리지 않는 경우(BOM·이진·ASCII)는 순위 대신 사유를 표시 (5.1.3 가드 표)
- ZIP 은 `이전 이름 → 새 이름` 목록을 보여주고, 이미 UTF-8 인 항목은 흐리게 구분
- **"파일이 멀쩡한데 내용이 깨진" 경우는 사유를 먼저 말한다.** 순위만 보여주면 왜 이런 결과가 나왔는지 알 수 없다. 근거 칩에 두 단계를 다 표시한다 — `utf-8 파일` → `windows-1252 되돌림` → `utf-8 로 읽기`
- **"정상입니다" 라고 단정하지 않는다.** 되돌릴 조합을 못 찾은 것과 정말 멀쩡한 것은 다르다. 글자가 깨져 보이는데 복구가 안 됐으면 그 사실과 이유(서로 다른 깨짐이 섞임 / 붙여넣기 손상)를 말한다
- **본문 예시 표는 언어를 골고루 싣는다.** 한국어만 있으면 "우리 언어도 되나" 라는 의문이 남는다. C1·NBSP 가 0개인 샘플은 어느 언어에나 있다 — C1 은 언어가 아니라 **오독 인코딩**의 속성이라(`latin1` 54%, 나머지 0%) 인코딩만 바꿔 고르면 된다
- **예시가 실제로 동작하는지는 사람이 아니라 테스트가 판정한다** (`test/examples.js`). 손으로 검증하다 틀린 설명을 실은 전례가 있다
- **파일이 붙여넣기보다 정확하다는 안내를 본문에 둔다.** 사용자는 보통 붙여넣기를 먼저 시도하는데, 그 앞단(메신저·터미널 경유)에서 C1 이 사라졌을 수 있다. 붙여넣기 창 자체가 문제인 것은 아니다 — 브라우저 안에서 복사·붙여넣기하면 C1 은 온전히 전달된다

**철회된 요구 — 예시 버튼**

원래 *"입력 즉시 예시 버튼 제공 (빈 화면에서 뭘 넣을지 모르는 문제 해결)"* 이 있었으나 제거했다. 입력창 우측 상단에 `한국어` `일본어` 같은 언어 이름 버튼이 놓이는 형태였는데, 그 자리는 웹 도구에서 관례적으로 **언어 전환기**가 있는 위치라 예시 로더가 아니라 UI 언어 탭으로 읽혔다. 다국어 지원(M3)이 로드맵에 있어 오해가 더 강했고, 프로젝트 소유자조차 용도를 알아보지 못했다.

**해결됨 (11차) — 본문 정적 예시 표.** 위에서 예고한 "버튼이 아닌 형태" 중 정적 표 쪽으로 풀었다. 본문에 깨짐 → 복구 예시 8행(한국어 3 · 일본어 1 · 중국어 1 · 독일어 1 · 러시아어 1)을 두고, `test/examples.js` 가 index.html 을 직접 파싱해 매번 검증한다. 입력창 주변에는 아무것도 붙이지 않았으므로 위 오인 문제가 재현되지 않는다.

**이 표를 다시 손댈 때 지킬 것**

- 표에는 **전체 문자열**을 싣는다. 축약형(`…`)을 쓰면 사람이 그대로 복사해 잘린 입력을 넣는다 — 실제로 그렇게 실패한 사례가 있다(5.1.2 관측 항목).
- `&#x80;` 같은 숫자 문자 참조로 C1 을 쓰지 않는다. HTML5 가 windows-1252 로 재매핑해 다른 글자가 된다.
- 언어를 골고루 싣는다. 한국어만 있으면 "우리 언어도 되나" 라는 의문이 남는다.

## 6. 기술 구조

### 6.1 스택

> **현황 — 빌드가 없다 (2026-08).** 아래 안대로 `build.js` 를 한 번 만들었다가 걷어냈다.
> 5페이지짜리 사이트에서 빌드가 버는 것은 푸터 11줄뿐인데(CSS 는 `styles.css` 로 빼서 이미 해결), 그 대가로 "원본과 산출물 두 벌" 이라는 개념이 생겨 **"약관을 어디서 고치냐" 는 질문이 세 번 반복됐다.** 지금은 `index.html` · `styles.css` · `content/*.html` 이 그대로 사이트다.
> **다국어(M3) 로 가면 5페이지 × 4언어 = 20장이 되어 빌드가 다시 필요해진다.** 그때 이 절을 다시 볼 것. 그전에 미리 만들지 말 것 — 이번 실수가 그것이었다.
>
> **갱신 (16차) — 다국어에 갔는데도 빌드는 필요 없었다.** 위 전제는 "페이지마다 로직이 복사된다" 였는데, 엔진과 화면 코드를 공유 파일로 빼고 나니 **복사되는 로직이 0** 이 됐다.
>
> ```
> engine.js · ui.js         모든 언어가 공유 (로직)
> i18n.<언어>.js            언어별 화면 문자열  ← 번역 대상
> index.html · en/index.html  언어별 본문(글) + <head>
> ```
>
> 언어별 파일에 남는 것은 **번역된 글과 문자열 객체뿐**이고, 그건 빌드로 만들어낼 수 있는 것이 아니다.
>
> **갱신 (17차) — 푸터 중복을 실제로 재봤다.** 일본어까지 붙어 **15장**이 되면서 "푸터를 고치면 15개 파일" 이라는 비용이 생겼다. "정적 사이트라 어쩔 수 없지 않나, 푸터도 번역해야 하니까" 라는 물음에 대한 답은 **절반만 그렇다** 이다.
>
> | | 장수 | 크기 |
> |---|---|---|
> | `index.html` | 1 | 330자 |
> | `en/index.html` | 1 | 574자 |
> | `ja/index.html` | 1 | 514자 |
> | `content/*.html` | 4 | 333자 (4장 바이트 동일) |
> | `en/content/*.html` | 4 | 415자 (동일) |
> | `ja/content/*.html` | 4 | 332자 (동일) |
>
> **서로 다른 푸터는 6종, 15벌로 퍼져 9벌이 순수 중복이다.**
>
> - **언어별 3종은 원리적으로 못 줄인다.** 푸터 문장·링크 이름·사이트명이 전부 번역 대상이라 빌드를 넣어도 번역문 3벌은 어딘가에 있어야 한다.
> - **6종인 이유는 번역이 아니라 경로 깊이다.** `content/` 에서는 `../index.html`, 루트에서는 `index.html` 이라 같은 언어가 두 벌이 된다. **이건 "더블클릭하면 열린다"(3.1)의 대가다** — 루트 기준 경로로 바꾸면 3종이 되지만 로컬에서 링크가 전부 죽는다.
>
> **JS 로 푸터를 그리는 방법은 기각했다.** 빌드 없이 중복이 사라지지만 개인정보처리방침·약관 링크가 HTML 소스에서 사라진다. 7장 체크리스트가 요구하는 것이 정확히 그 링크라 감수할 자리가 아니다. **간단해 보여서 나중에 다시 꺼내기 쉬우므로 기각 사유를 여기 남긴다.**
>
> **지금은 15장이므로 그대로 두고, 언어를 하나 더 붙여 20장이 되는 시점에 빌드를 다시 검토한다** — 이 절이 원래 적어둔 경계와 같다. 그전까지는 링크 전수 검사 스크립트로 빠뜨림을 잡는다.
>
> **갱신 (18차) — 허브 3장이 붙어 18장이 됐고, 푸터는 여전히 6종이다.** 도구 페이지가 자기 언어 루트에 파일식으로 놓이므로 **경로 깊이가 안 늘어난다**(3.1 갱신 상자). 도구를 몇 개 붙여도 6종은 그대로다.
>
> 다만 **20장 경계가 코앞이다.** M4 도구 4개를 붙이면 3언어 × 4 = 12장이 더해져 30장이 되고, 그때는 푸터 6종 × 30벌 + `<head>` 중복이 손으로 감당할 규모를 넘는다. **M4 진입과 빌드 재검토가 같은 시점이라고 보면 된다.**
>
> 링크 전수 검사는 `test/links.js` 로 실제로 만들었다(`npm run check:links`, `npm test` 의 첫 단계). 파일 존재뿐 아니라 **canonical·hreflang·언어 전환기·푸터가 자기 언어의 같은 페이지를 가리키는지**까지 본다 — 언어가 섞인 링크는 살아 있어서 눈으로도 테스트로도 안 잡히던 자리였다.


프레임워크 없음. Node 빌드 스크립트로 정적 HTML 생성.

```
index.html             도구.  푸터에서 content/ 로 연결
styles.css             5개 페이지가 공유하는 유일한 스타일
robots.txt
content/
  about.html           법적 페이지 4개.  완성된 페이지이지 조각이 아니다
  privacy.html
  terms.html
  contact.html
test/                  개발용. 배포 안 감
```

**변환 단계가 없다.** 파일을 브라우저로 열면 그게 곧 실제 화면이고, 배포는 위 파일들을 그대로 올리면 끝이다.

대가는 하나 — **푸터가 5개 파일에 각각 들어 있어** 고칠 때 다섯 곳을 같이 고쳐야 한다. CSS 는 `styles.css` 로 빠져 있어 중복이 없다.

**다국어(M3) 로 가면 5페이지 × 4언어 = 20장이 되어 손으로 관리가 안 된다.** 그때 위의 마크다운+템플릿 안을 다시 꺼내 쓴다. 그전에 미리 만들지 말 것.

### 6.2 배포

Cloudflare Pages 또는 Netlify. Git push → 자동 빌드. 서버 비용 0.

> **외부 요청은 Google Fonts 하나뿐이다** (`fonts.googleapis.com`, `fonts.gstatic.com`). 글꼴을 받는 과정에서 접속 IP 가 Google 로 가므로 개인정보처리방침에 명시했다. 자체 호스팅하면 외부 요청이 0 이 되어 그 항목을 지울 수 있고 LCP 에도 유리하다 — M1 범위 밖으로 뒀다.

### 6.3 성능 목표

| 항목 | 목표 |
|---|---|
| LCP | 2.0s 이하 |
| CLS | 0.05 이하 |
| 도구 JS 번들 | 30KB 이하 (gzip) |

**현재 24.1KB (2026-08). 여유 약 6KB.**

> ⚠ **전체 파일 크기와 섞어 세지 말 것.** 이 기준은 **자바스크립트**에 대한 것이다.
> `index.html` 전체는 gzip 28.6KB 인데, 거기엔 HTML 본문 5.1KB 가 같이 들어 있다.
> 둘을 헷갈려 "여유 1.4KB" 라고 잘못 인용한 적이 있고, 그 숫자로는 M6(언어 모델)이
> 불가능해 보인다. 판단이 갈리는 숫자라 재는 방법을 적어둔다 —
> **`<script>` 블록만 떼어내서 gzip 한다.**

| | 원본 | gzip |
|---|---|---|
| 자바스크립트 (엔진 + UI) | 52,678자 | **24,095B** ← 이것이 기준 |
| HTML 본문 | 8,899자 | 5,088B |
| `index.html` 전체 | 61,594자 | 28,560B |

역변환 테이블은 최초 사용 시점에 생성(현재 구현대로 지연 생성 유지). 웹폰트는 `font-display: swap`.

## 8. 마일스톤

**M0 — 엔진 정확도 수정 (완료)**
5.1.1의 2줄 패치 적용. 벤치마크 스크립트를 회귀 테스트로 저장. 이후 4~6차에서 계측 결함을 잡고 재측정 — 현재 148건 브라우저 기준 84.5% (후보 3개 내 96.6%)

**M0.5 — 파일 입력 (완료, 9차)**
`recoverBytes` / ZIP 파일명 복구 + `붙여넣기`·`파일` 탭. 5.1.3 참고. 브라우저 기준 1순위 75.3% / 후보 3개 내 88.3%.
페이지 분리는 안 했다 — 빌드 구조가 없어 M1 이후로 미룬다.

**M1 — 승인용 최소본** *(도메인 확보, 배포 대기)*
법적 페이지 4개 + 푸터 링크 + 본문 SEO — **완료**. 도메인(`prelaps.com`)도 확보했고, 그것에 묶여 있던 항목을 18차에서 전부 처리했다 — `canonical` · `hreflang` 4줄 · `og:url` · `og:image` · `sitemap.xml` · `robots.txt` 의 사이트맵 줄. 남은 것은 **배포와 Search Console 등록**이다.

**빌드는 만들었다가 걷어냈다.** 6.1 참고 — 5페이지 규모에서 빌드가 버는 것은 푸터 11줄뿐인데, "원본과 산출물 두 벌" 이라는 개념 때문에 "약관을 어디서 고치냐" 가 세 번 반복됐다. `sitemap.xml` 과 canonical 은 손으로 만들었고, 어긋남은 `test/links.js` 가 잡는다.

**엔진 모듈화도 하지 않았다.** `src/engine/*.js` 분리는 "엔진 원본은 index.html" 규칙과 `test/sync.js` 를 깨뜨려 벤치마크 4개를 멈추게 한다. 사용자 이득이 0이라 M3 로 미뤘다.

본문 분량은 도구 페이지 2,865자로 기준(1,500자)의 191%다. 법적 페이지는 679~1,316자인데, 1,500자 기준은 **도구 페이지**에 대한 것이고 법적 문서를 늘리는 건 필러가 된다.

**M2 — 애드센스 신청**
Search Console 색인 확인 후 신청. 반려 시 사유별 대응

**M3 — 다국어** *(구조 완료, 16차 / 언어 추가는 진행 중)*

근거는 2.5절 — 차별점이 CJK인데 UI가 한국어 전용인 모순을 먼저 해소해야 한다.

**구조는 끝났다.** UI 문자열은 25개가 아니라 **109개**였고(추정보다 4배), 엔진 안에도 사용자 노출 라벨이 20개 더 있었다. 전부 `I18N` 으로 뺐다.

```
engine.js · ui.js     모든 언어 공유.  로직 복사 0
i18n.<언어>.js        언어별 문자열  ← 새 언어는 이 파일 하나 + 페이지 한 장
```

- **`/en/` · `/ja/` 완료** (초안, 검수 대기). 한국어는 루트 유지
- `/ja/` 를 먼저 붙인 근거는 2.5절 — 문자화け 검색량이 최대이고 차별점이 CJK 다
- **다음 후보는 `/zh/`** (`gbk`·`big5` 오독이 벤치에서 큰 구간)
- **폴더는 언어 코드로** — `kr`·`jp` 가 아니라 `ko`·`ja`. 나라 코드를 쓰면 `hreflang` 이 무효가 된다
- **언어 전환 링크는 화면 최상단 오른쪽에 있다**(`.langsw`). 언어 이름은 번역하지 않고 각 언어의 자기 이름(`한국어`·`English`·`日本語`)을 쓴다
- **`hreflang` 은 아직 없다** — 절대 URL 이 필요해 도메인 대기(3.1). `canonical`·`sitemap`·`og:image` 와 같은 시점에 세 페이지에 함께 넣는다
- **법적 페이지도 3언어 완료** — `content/` · `en/content/` · `ja/content/` 각 4장. 사이트는 총 **15장**
- **준거법은 세 언어 모두 대한민국 법률**이다. 운영자 소재지 기준이라 언어를 바꿔도 달라지지 않는다
- **아동 조항은 나이를 못 박지 않았다** — 한국어판의 「만 14세 미만」은 국내법 기준이고 COPPA(13세)·GDPR(13~16세)과 어긋난다. 세 언어 모두 「연령을 불문하고 개인정보를 수집하지 않는다」로 서술했다
- **번역문은 초안이다** — 각 `i18n.*.js` 와 법적 페이지에 검수 필요 표시를 달아뒀다

**M4 — 도구 확장**
`/csv.html`, `/detect.html`, `/convert.html` 추가. 각각 본문 작성.
`/csv.html` 는 새로 만드는 게 아니라 **현재 `/` 의 파일 탭을 떼어내는 작업**이다. `/zip.html`(압축 파일명) 을 추가 후보로 검토.

**M5 — 최적화**
검색어 데이터 기반으로 본문 보강, 광고 위치 A/B

**M6 — 언어 모델** *(5장 본문이 오래 "M5" 라고 부르던 항목)*

`score()` 는 문자 *종류*의 비율만 본다. 그래서 `안녕하세요` 와 `똠뷁쨉먄` 이 **동점**이다(둘 다 100% 한글). 글자 **쌍**이 그 언어에서 얼마나 흔한지를 알면 갈린다.

지금 못 푸는 것 네 개가 **전부 이 하나에서 나온다.**

| | |
|---|---|
| 5.1.2 | 짧은 입력에 근거 없는 확신도가 붙는 문제 |
| 5.1.3 | 파일 모드에서 단일바이트 12종이 완전 동점 |
| 5.1.4 | 내용 깨짐의 동점 계열 (`Ñåãîäíÿøíåå` = `Сегодняшнее`) |
| 5.1.6 | 정상 글자와 깨진 글자가 **같은 문자**일 때 구간 경계를 못 찾음 |

**미뤄둔 이유는 용량이었고, 그 추정이 과대평가였다.** 5.1.2 는 "언어당 수십 KB" 로 봤는데, Firefox 의 `chardetng` 는 풀 n-gram 이 아니라 **거칠게 분류한 문자의 "쌍" 빈도**로 30개 인코딩을 **62KB** 에 담는다(15차 조사). 6.3 의 JS 예산에 여유가 약 6KB 있으므로, 한국어·일본어로 좁히면 들어갈 여지가 있다.

> **번호를 M5 로 쓰지 말 것.** 5장 본문 6군데가 이 항목을 `M5` 로 부르고 있었는데 8장의 M5 는 최적화라, 읽는 사람이 "광고 A/B 를 하면 단일바이트 동점이 풀리나" 가 됐다. 실제로 혼동이 발생해 16차에서 M6 으로 분리했다.

## 9. 미결정 사항

1. ~~**도메인**~~ — **결정됨(18차): `prelaps.com`.** `https://` · **non-www** 로 통일하고 `www` 는 리다이렉트한다. 이 도메인은 깨진 글자 복구기 전용이 아니라 **여러 도구가 나눠 쓴다** — URL 설계 변경은 3.1 의 갱신 상자 참고.
2. ~~**`/csv.html` 파일 처리 범위**~~ — **결정됨(9차): 20MB 상한.** 판별은 앞 64KB 샘플로 하고 확정된 인코딩으로 전체를 디코딩한다. 상한을 넘으면 거부하고 안내한다. 브라우저 메모리로는 더 큰 파일도 가능하지만, 후보 3개를 각각 전체 디코딩하므로 문자열 사본이 3벌 생긴다는 점에서 잡은 값이다. 실사용 불만이 나오면 재검토.
3. ~~**다국어 번역 방식**~~ — **결정됨(16차): 초안을 직접 작성하고, 배포 전에 사람이 검수한다.**

   기계번역을 그대로 올리지 않는다는 원칙은 그대로다(저품질 콘텐츠 판정 위험). 대신 "번역"이 아니라 **해당 언어로 새로 쓰는 것**에 가깝게 간다 — 한국어 본문은 "복구가 안 되나요" 부터 시작하는데, 이건 한국어로 검색해 들어와 실패한 사람을 위한 순서다. 영어권 사용자는 ftfy 를 이미 알고 올 가능성이 높아 같은 순서가 최선이라는 보장이 없다.

   현재 `i18n.en.js` 와 `en/index.html` 에 초안이 들어가 있고 **파일 첫머리에 검수 필요 표시**를 달아뒀다. 도메인이 없어 아직 배포되지 않으므로 시점 여유는 있다.
4. **쿠키 동의 배너** — 자체 구현 vs CMP 도입. 현재 쿠키를 하나도 쓰지 않으므로 배너가 필요 없고, 개인정보처리방침에 "광고 도입 시 이 문서를 먼저 갱신한다" 고 적어두었다. 광고를 붙이는 시점에 결정한다
5. ~~**애널리틱스**~~ — **결정됨: Search Console + Cloudflare Web Analytics. GA4 는 쓰지 않는다.**

   **둘은 보는 것이 달라 서로를 대체하지 못한다.**

   | | 무엇을 보나 |
   |---|---|
   | Google Search Console | 검색 결과에서 우리를 **본** 사람 — 검색어·노출 수·순위·클릭률 |
   | Cloudflare Web Analytics | 사이트에 **온 뒤** — 방문자 수·페이지뷰·유입처·국가 |

   Cloudflare 쪽에는 **들어온 사람만** 잡힌다. "한글 깨짐" 으로 검색했는데 우리가 8위라 안 눌렀다면 아무 흔적이 없다. SEO 를 고치려면 Search Console 이 필수다.

   **GA4 를 안 쓰는 이유 셋** — ① 쿠키를 써서 동의 배너가 필요해지고 개인정보처리방침의 "쿠키 없음" 도 고쳐야 한다 ② 스크립트가 무거워 6.3 의 LCP 2.0초 목표에 부담 ③ 페이지 5개짜리 사이트에서 알고 싶은 것은 위 두 도구로 충분하다. 무엇보다 **"입력이 서버로 가지 않는다"는 차별점과 방문자 상세 추적은 어긋난다.**

   "파일 탭을 아무도 안 쓰는 것 같다" 같은 구체적 질문이 생기면 그때 다시 검토한다.
